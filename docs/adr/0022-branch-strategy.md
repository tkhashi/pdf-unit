# ADR 0022: development を既定ブランチにし、作業ブランチから PR で取り込む

- ステータス: 採用
- 日付: 2026-09-26

## コンテキスト

これまでは作業ブランチを手元で `main` にマージして push していました。ADR 0021 で `main` への push が AWS への自動デプロイになったため、`main` への反映は本番への反映と同じ意味になりました。

実装は主にエージェント(Claude Code)が行う想定です。次の運用を、文書で依頼するだけでなく仕組みとして守らせたいという要件がありました。

- 既定ブランチを `development` にする
- 作業は `feat-` で始まるブランチで行い、完了したら PR で `development` にマージする(エージェントが PR を作成し、そのままマージする)
- `main` へのマージは手動、または明示的な指示があったときのみ行う
- PR の本文は日本語で簡潔に書く。テンプレートを事前に定義し、gh コマンドで作成する

対象はこのリポジトリのみです(`pdf-unit.infra` は手動の `cdk deploy` で運用しているため対象外)。

## 決定

- **ブランチ**: `development`(既定)・`main`(本番)・作業ブランチ。作業ブランチの接頭辞は `feat-`・`fix-`・`docs-` の3種類とします(不具合修正と文書のみの変更も区別できるように、`feat-` 以外も認めました)
- **マージ方式**: 作業ブランチ → `development` は squash、`development` → `main` は merge commit
- **ルールと仕組みの置き場所**: 強制したいことは機械的な仕組みに、手順と文面は文書に置きます
  - GitHub のルールセット: `main`・`development` とも PR 必須(承認数 0)、force push・削除を禁止。管理者はバイパス可
  - `.github/pull_request_template.md`: PR 本文の型
  - `CLAUDE.md`: ルールの要約(常に読み込まれるので短くする)
  - `.claude/skills/pr/SKILL.md`: PR 作成〜マージの手順
  - Claude Code の PreToolUse フック(`.claude/hooks/guard-git.sh`): 違反する git/gh 操作を実行前に拒否(deny)または確認(ask)する

## 理由

- **GitHub のルールセット**は、エージェントの判定を迂回した操作や人の誤操作も止められる唯一の層です。承認数を 0 にしたのは、エージェントが自分で作った PR をマージする運用のためです(GitHub では PR の作成者は自分の PR を承認できません)
- **フック**は、エージェントが違反に気づかず操作した場合に、GitHub に拒否される前の段階で理由付きで止めます。`main` 向けの操作を拒否ではなく確認(ask)にしたのは、「指示があったときのみ」をユーザーの確認で担保するためです。フックはコマンド文字列の簡易判定なので、迂回を防ぐものではなく、ルールセットと併用します
- **skill** に手順を置くのは、CLAUDE.md を常に読まれる要約に保ち、PR 作成時にだけ詳細な手順(テンプレートの埋め方、rebase、マージ後の後片付け)を読み込ませるためです。本文は `gh pr create --body-file` で渡します(`gh pr create` のテンプレート自動適用は対話モードでしか働かないため、テンプレートを読んで埋めた本文をファイルで渡します)
- **PR テンプレート**を `.github/` に置くのは、GitHub の画面から PR を作る場合にも同じ型が使われるためです
- **git の commit hook(`pre-commit` 等)は採用しません**。`.git/hooks` はバージョン管理されず、`core.hooksPath` の設定を各自の手元で行う必要があります。また人が手動で行う操作も妨げやすく、ルールセットとフックで目的を満たせます
- **マージ方式**: 作業ブランチを squash すると `development` の履歴が PR 単位になり読みやすくなります。一方 `development` → `main` を squash すると、両ブランチの履歴が分かれて次回の反映で衝突しやすくなるため merge commit にします

## 影響

- `development` へのマージではデプロイは走りません。本番への反映は `main` への PR のマージ時です(`.github/workflows/deploy.yml` は変更なし)
- ルールセットはリポジトリが公開(public)であることを前提にしています。非公開にすると、GitHub の無料プランではルールセットが効かなくなり、フックだけが防衛線になります
- フックは `jq` を使います。git/gh を含まないコマンド、このリポジトリ以外で動くコマンドは検査しません
- 既存の `feat/...` 形式のブランチは過去のものとして残します。新しいブランチには新しい命名規則を使います
