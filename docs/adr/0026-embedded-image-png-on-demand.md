# ADR 0026: 埋め込み画像の PNG 化を、要求された1枚だけに絞る

- ステータス: 採用
- 日付: 2026-09-26

## コンテキスト

埋め込み画像(ADR 0010)は、`/api/page/lines` が配置情報を返し、UI が画像ごとに `/api/page/images/{k}` で画像データ(PNG)を取得します。サーバーはステートレスなので、どちらの API も毎回ページ内の全画像を走査します。

変更前は、どちらの API でも全画像について画像データの取り出し(`get_bitmap`)と PNG 化を行っていました。`/api/page/lines` は配置情報しか使わないのに全画像を PNG 化し、`/api/page/images/{k}` は1枚を返すために全画像を PNG 化していました。UI は画像の数だけ `/api/page/images/{k}` を同時に要求するため、画像 N 枚のページでは PNG 化が N² 回行われます。

ADR 0023 の計測で、埋め込み画像を61枚含むページでは次のとおりでした。

- `/api/page/images/{k}` 1回あたり約84ms。うち約48ms が PNG 化、約21ms が画像データの取り出し
- 61回の合計は約5.1秒

## 決定

- `extract_page_images` に `png_indices`(PNG 化する画像番号)を加えます。
  - `/api/page/lines` は PNG 化しません。
  - `/api/page/images/{k}` は k 番の画像だけを PNG 化します。
- 画像データの取り出し(`get_bitmap`)は、PNG が不要な画像でも変更前と同じく全画像で行います。

## 理由

- **画像番号を変えないため**: 画像データを取り出せない画像(`PdfiumError`)は飛ばして、画像番号を詰めています。取り出しまで省くと、どの画像が飛ばされるかが分からなくなり、画像番号(`ImageRecord.index`)が変わりえます。取り出しは続け、時間の大半を占める PNG 化(`to_pil`・回転・PNG エンコード)だけを絞ります。`to_pil` は `PdfiumError` を投げない(PIL の `frombuffer` のみ)ため、`try` の外に移しても飛ばされる画像は変わりません。
- **出力を変えないため**: PNG 化の処理自体は変更前と同じなので、返す PNG はバイト単位で同じです(ADR 0023 の方針)。
- **検証**: ADR 0023 と同じ10ページ(埋め込み画像61枚すべてを含む)で、全 API の応答ボディ105件がバイト単位で一致しました。
- **効果**(手元での計測、61枚のページ):
  - `/api/page/images/{k}`: 1回あたり 84ms → 44ms、61回の合計 5.1秒 → 2.7秒
  - `/api/page/lines`: 197ms → 147ms

### 採らなかった案

- **k 番の画像を PNG 化した時点で走査を打ち切る**: 取り出す画像がさらに平均で半分になりますが、配置情報が途中までしか作られない状態を許すことになり、関数の約束事が複雑になります。残りの取り出し時間は1回あたり約20ms のため見送りました。
- **複数の画像を1回の API でまとめて返す**: リクエストの回数と Lambda の同時起動数は減りますが、API と UI の変更になり、応答上限(6MB)に収まるように分割する処理も必要です。別途検討します。

## 影響

- API の仕様と応答は変わりません。
- 画像の数だけ `/api/page/images/{k}` を同時に要求する構成は変わりません。Lambda では画像数と同じ数の実行環境が同時に起動しうる点は残ります。
- 計測の件数は、`images_px`(全画像の画素数)に代えて `images_png_px`(PNG 化した画像の画素数)を記録します。
