# ADR 0028: 状態は Zustand の1つの store と純粋関数の reducer で持ち、描画は React の外で行う

- ステータス: 採用
- 日付: 2026-09-26

## コンテキスト

React へ移行するにあたり([0027](0027-frontend-react-typescript.md))、状態の置き場所を決める必要がありました。要件は次のとおりです。

- コンポーネントは状態を極力持たず、上位のレイヤーで状態を管理する。処理はイミュータブルを意識する
- 1ページに10万要素を超えることがある図面で、パン・ズーム・ホバー(毎フレーム発生しうる)の応答性を旧UIより悪くしない
- 旧UIの挙動(古い応答を捨てる条件、ホバーだけならハイライトの Canvas だけ描き直す、など)を変えない

`useReducer` + Context も検討しましたが、ホバーや表示倍率が変わるたびに Context を読むコンポーネントがすべて再レンダーされ、メモ化や Context の分割で補う手間が大きいと判断しました。

## 決定

依存の向きは `components` ← `containers` ← `state`・`controllers` → `services`・`domain`、`render` → `domain` とします(`web/src/`)。

- **`domain/`**: DOM・React に依存しない純粋関数。旧UIのロジック(形状の比較、クリックで辿る属性、空間インデックスとヒット判定、選択、属性パネルの行、表示変換、文言)を、定数・走査順・文字列を変えずに型付きで移した。Vitest で検査する
- **`state/`**: Zustand の vanilla store を1つだけ持ち、変更は `dispatch(action)` → 純粋関数 `reduce(state, action)` だけで行う。reducer は変更が無ければ元の state をそのまま返す。古い文書・古いページへの応答を捨てる判定(文書の番号・ページ要求の通し番号・ページ番号の照合)も reducer が行う
- **ページのモデル(`PageModel`)**: 要素の配列・空間インデックス(`Float64Array` 等)は大きいため、作成後は書き換えず参照で受け渡す。型は `readonly` にし、実行時の凍結(`Object.freeze`)はしない。作成する関数の中だけでローカルに書き換える
- **store に入れないもの**: pdf-lib の文書・ページPDFのキャッシュ・`Path2D`・埋め込み画像の `HTMLImageElement`(ブラウザの可変オブジェクト)と、1フレーム以内に何度も変わる値(マウス位置・ドラッグの起点)。前者は `services`・`render` がモデルや文書の同一性をキーに持ち、後者は入力を処理するコントローラーのクロージャに持つ
- **`controllers/`**: 非同期処理と入力(文書を開く、ページの読み込み、原本画像の解像度段階、サムネイルのバッチ取得、表示領域の操作、ツールチップ)。API の呼び出しは操作(アクション)を起点に行い、`useEffect` からは呼ばない(StrictMode で effect が2回動いても要求が重複しないように)
- **`render/`**: store を `subscribe` し、`requestAnimationFrame` で1フレームに1回だけ Canvas を描く。線・文字・画像の層は、文書・ページのモデル・表示変換・表示対象・選択の有無が変わったときだけ描き直し、ホバー・選択だけが変わったときはハイライトの層だけを描く(旧UIの `requestRender(vectors)` と同じ)。`Path2D` のバッチはモデル・選択の同一性をキーに `WeakMap` で作り置きする。原本画像を載せた要素の `transform` も購読の中で直接書く
- **`components/`**: props だけを受け取る表示用のコンポーネント。状態を持たない(チェックボックスの `indeterminate`、ツールチップの位置、選択ページへのスクロールのような DOM への反映だけを ref・layout effect で行う)
- **`containers/`**: 画面の領域ごとに store の一部を selector(`useShallow`)で購読し、components へ props を渡す。ホバーやパンで無関係な領域を再レンダーしない

## 理由

- 状態の変化がすべて action と純粋関数で表されるため、どの操作で何が変わるかを reducer だけで追え、単体テストで検査できる
- Zustand の selector 購読により、再レンダーは値が変わった領域だけに限られる。Canvas の描画・パンは React の再レンダーを通らないため、旧UIと同じ手順・同じ頻度で描ける
- 大きなモデルを複製・凍結しないことで、イミュータブルな扱いと性能を両立できる(同一性の比較でメモ化もできる)

## 影響

- ページのモデルを後から書き換えるコードを書いてはいけない(型で `readonly` にしているが、実行時には防げない)
- 表示領域の大きさを測る前に React の変更を DOM へ反映する必要がある箇所(文書を開いた直後・ページ切替)は `flushSync` を使う(旧UIは同期的に DOM を書き換えてから `clientWidth` を読んでいたため)
- store の購読の中で dispatch すると、後続の購読者には古い state が引数で渡ることがある。DOM へ書く値は `getState()` から読む
