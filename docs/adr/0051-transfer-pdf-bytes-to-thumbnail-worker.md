# ADR 0051: サムネイル用 Worker へは、読み込んだPDFのバイト列を複製せずに譲り渡す

- ステータス: 採用
- 日付: 2026-10-01

## コンテキスト

[0041](0041-thumbnail-client-side-rendering.md) では、`openThumbnailSource` が受け取ったバイト列を複製(`slice()`)してから Worker へ転送していた。呼び出し側のバイト列に影響させないためである。

文書を開くとき、本体側には次の3つが同時にあった。

1. ファイルから読んだバイト列(`file.arrayBuffer()`)
2. pdf-lib が読み込み時に複製して持つストリームの中身
3. Worker へ送るための複製

いずれもPDFと同じ大きさなので、開いている間の本体側のピークはPDFの大きさにほぼ比例して3倍分になる。[0048](0048-thumbnail-worker-page-cleanup.md) と同じ合成PDF(73MB)で、開いてから1ページ目を表示するまでの本体側の JS ヒープの最大(GC を挟まずに 100ms ごとに計測)は 191MB だった。

pdf-lib 1.17.1 のパーサーは、ストリームの中身・解釈できないオブジェクトを `Uint8Array.prototype.slice`(複製)で切り出す。`subarray` を使うのは、デコード後のバッファに対してだけである。そのため読み込みが終われば、1のバイト列は pdf-lib から参照されない。

## 決定

- `openThumbnailSource(data: ArrayBuffer)` は、受け取ったバイト列を複製せずに Worker へ転送する。呼び出した後、呼び出し側の `data` は空(detached)になる
- `controllers/document.ts` は、pdf-lib で読み込んだ後のバイト列(1)をそのまま渡す

## 理由

- 1のバイト列は、pdf-lib の読み込みと Worker への受け渡しにしか使わない。読み込んだ後に Worker へ譲れば、複製(3)は要らない
- 出力に影響しないことを確かめた。合成PDF 30ページすべてについて、サーバーへ送る切り出しPDF(`/api/page/lines` の本文)の SHA-256 が変更前と一致した。サムネイルの PNG も一致した。E2E の新旧比較(`pnpm e2e:parity`。送ったPDFの SHA-256 の比較を含む)もすべて通った

## 影響

- 同じ合成PDFで、開いてから1ページ目を表示するまでの本体側の JS ヒープの最大は 191MB から 122MB になった(ほぼPDF1つ分)。開いた後に落ち着いた状態の値は変わらない(1は変更前も、文書を開く処理が終われば解放されていた)
- pdf-lib を更新して、読み込んだバイト列を参照し続けるようになった場合は、この受け渡しをやめて複製に戻す必要がある。更新時は、切り出したPDFの SHA-256 が変わらないこと(`pnpm e2e:parity`)を確かめる
