# ADR 0014: フォント名の文字コードは確実な情報源から順に判定する(提案)

- ステータス: 提案(未実装)
- 日付: 2026-09-25

## コンテキスト

テキストにマウスオーバーしたときのフォント名が文字化けすると指摘され、文字コードによってデコード方法が変わる中で全てに対応するにはどうすればよいか相談された。

- PDF のフォント名(`BaseFont`)は、文字コードの宣言を持たない生のバイト列。仕様上は UTF-8 が推奨だが、日本語 Windows の古いソフトは Shift_JIS 系(cp932)で書き込む
- 問題の図面は `b'JVUQGE+\x82l\x82r\x83S\x83V\x83b\x83N'`(cp932 で「ＭＳゴシック」)
- pdfminer は UTF-8 で読めないと `str(bytes)` を使うため、`"b'...\x82l...'"` という文字列がそのまま表示されていた
- 同じバイト列が gbk(`俵俽僑僔僢僋`)や cp949(`굃굍긕긘긞긏`)でもエラー無く読めてしまうため、文字コードの総当たりでは誤判定を防げない

## 決定(提案)

確実な情報源から順に使う。

1. pdfminer の `"b'...'"` 文字列を `ast.literal_eval` で元のバイト列に戻す(損失なく戻せる)。UTF-8 で読めればそれを使う
2. 埋め込みフォント(TrueType / OpenType)の `name` テーブルにある、UTF-16 と言語コード付きのフォント名を使う(`fontTools` を依存に追加)
3. `CIDSystemInfo` の `Ordering` と `Encoding` の CMap 名から文字コードを決める(`Japan1` / `90ms-RKSJ-H` → cp932、`GB1` → gbk、`CNS1` → big5、`Korea1` → cp949)
4. ページ本文の言語から候補の優先順位を決め、デコード結果がその言語の通常の文字範囲に収まるものを選ぶ
5. 決まらない場合は、推測した文字列を出さず PDF の名前表記(`JVUQGE+#82l#82r…`)で表示する

あわせて、クリック巡回の「フォント」の一致判定は元のバイト列で行い、表示だけを読みやすい名前にする。推測で決めた場合は情報源(例: 推定 cp932)を添える。

## 理由

- 埋め込みフォントの `name` テーブルは文字コードが明示されているので最も確実。問題の図面のフォントも TrueType(`FontFile2`)が埋め込まれている
- 問題の図面の `CIDSystemInfo` は `WinCharSetFFFF` で手掛かりにならないため、3だけでは不十分
- 一致判定をバイト列で行えば、表示名の推測が外れても同属性判定は正確なまま

## 影響

- 実装する場合、依存に `fontTools` が加わる
- 現状は README の既知の制約に記載している
