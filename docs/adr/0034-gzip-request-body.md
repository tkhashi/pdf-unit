# ADR 0034: gzip で圧縮したリクエストボディを受け付ける

- ステータス: 採用(サーバー側。UI から圧縮して送る対応は Issue #8)
- 日付: 2026-09-26

## コンテキスト

API に1回で送れる PDF(1ページを切り出したもの)は 4MB が上限です(Lambda の同期呼び出しのリクエスト上限6MB と、関数URLによる base64 化のため。ADR 0019・0020)。この上限を超えるページは処理できません。

実際の図面 PDF 3種(計117ページ)では4ページが該当しました(切り出し後 4.69MB〜10.32MB)。原因は小さな画像が大量にあることで、描画されない余分なリソースは含まれていませんでした。そのため、切り出し方を変えても小さくはなりません(Issue #8)。

一方、切り出した PDF を gzip で圧縮すると、4ページ中3ページが上限内に収まりました(4.69MB→3.11MB、4.93MB→1.10MB、7.26MB→2.30MB)。残りの1ページは 10.32MB→4.53MB で、圧縮しても収まりません。

## 決定

- リクエストの `Content-Encoding: gzip` を受け付け、サーバー(`pdf_body`)で展開してから、これまでと同じ検証と処理を行います。
- 上限 4MB(`MAX_PDF_BYTES`)は、送られてきた(圧縮後の)大きさにかけます。
- 展開後の上限 `MAX_DECOMPRESSED_PDF_BYTES`(64MB)を設けます。展開は上限+1バイトで打ち切り、超えたら 413 を返します。
- 次の場合は 400 を返します: 壊れた gzip、途中で切れた gzip、複数の gzip を連結したボディ。gzip 以外の圧縮形式は 415 を返します。
- 圧縮されていないリクエストの扱いは変えません。
- 展開はスレッドプールで行い、イベントループを止めません。
- `scripts/smoke_test.sh` で、圧縮したリクエストが CloudFront・Lambda Web Adapter を通っても届き、圧縮なしと同じ応答になることを確かめます。

## 理由

- **Lambda の上限は転送される大きさにかかる**: 圧縮して送れば、同じ上限のまま、より大きなページを送れます。infra の変更(S3 経由のアップロードなど)も要りません。
- **出力が変わらない**: 可逆圧縮を展開してから処理するので、応答は圧縮なしで送った場合とバイト単位で同じです(ADR 0023 の方針)。
- **圧縮爆弾への備え**: 小さな gzip が巨大なデータに展開される入力で、メモリを使い果たさないよう、展開後の大きさで打ち切ります。64MB は、送信上限 4MB の PDF が圧縮で縮む範囲を十分に超え、Lambda のメモリ(2048MB)に対して余裕のある値です。
- **ブラウザで圧縮できる**: UI は標準の `CompressionStream('gzip')` で圧縮して送れます。`x-amz-content-sha256` は圧縮後のボディで計算します。

### 採らなかった案

- **S3 経由でアップロードする**: 送信上限そのものを外せますが、infra の変更(バケット・署名付き URL の発行・権限)と、サーバーがステートレスである方針(ADR 0019)の見直しが要ります。圧縮で大半のページが収まるため、今回は見送りました。圧縮しても収まらないページが問題になった場合に改めて検討します。
- **展開後の上限を設けない**: 圧縮爆弾でメモリを使い果たすおそれがあるため採りません。

## 影響

- UI が圧縮して送るようになるまで、挙動は変わりません(Issue #8)。
- 検証: 変更前後で、圧縮なしのリクエストへの応答105件(ADR 0023 と同じページ)がバイト単位で一致しました。圧縮したリクエストへの応答は、圧縮なしの応答(5ページ×3種類の API)とバイト単位で一致しました。4MB を超えて送れなかったページのうち3ページは、圧縮して送った応答が関数の直接呼び出しの結果と一致しました。
- 4MB を超えて送れないページのうち、描画される画像が1,000枚を超えるものは、UI が画像を1枚ずつ要求すると要求数が膨大になります。圧縮して送る対応は、埋め込み画像のまとめ取得(ADR 0032、Issue #9)を UI が使うようになってから行います。
