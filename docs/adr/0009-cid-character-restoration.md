# ADR 0009: `(cid:N)` と出る文字は PDFium の文字解釈で補完する

- ステータス: 採用
- 日付: 2026-09-24

## コンテキスト

テキストが「cid:34」のように表示されると指摘された。問題のPDF(PDFTron 生成)は1ページ目の全7,649文字が `(cid:N)` だった。

- フォントは `Type0 / Identity-H`、下位フォントは `CIDFontType0`(`CIDSystemInfo = PDFTron-Identity`)で、文字コードをUnicodeへ変換する対応表(ToUnicode CMap)を持たない
- pdfminer は変換できない文字を `(cid:N)` という文字列で返す
- このPDFでは CID 値そのものが Unicode だった(`35373` = 設、`22259` = 図)。PDFium は独自のフォールバック処理で正しい文字を返せる

## 決定

- `(cid:N)` の文字だけを補完してから単語にまとめる
  1. PDFium で全文字の Unicode と文字原点を取得する(PDFium が補った空白・改行は除く)
  2. pdfplumber の文字を、原点(0.1pt単位、隣接セルも探索)で突き合わせて置き換える
  3. 突き合わせられない文字は、同じフォントで突き合わせた文字がすべて `chr(CID)` と一致した場合に限り `chr(CID)` で補う
- `chr(CID)` を無条件には使わない

## 理由

- CID がグリフ番号である一般的な Identity-H フォント(`cid:34` など小さい値)で `chr(CID)` を使うと誤変換になる。PDFium はフォント内部の cmap 等から復元できる範囲が広いので、先に PDFium を使う
- 最後の手段を「CID が Unicode と確認できたフォント」に限れば、PDFium が空白を生成文字扱いして拾えない場合も安全に補える

## 影響

- 問題のPDFは 7,604/7,649 文字を突き合わせで、残り45文字(空白)を `chr(CID)` で復元し、2,235語すべてが正しく表示された
- 補完でページごとに PDFium の処理が増えた(問題の図面で約4秒)。PDFium を並行して呼ぶ機会も増え、[0011](0011-pdfium-thread-safety.md) の問題が表面化するきっかけになった
