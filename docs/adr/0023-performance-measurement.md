# ADR 0023: 高速化の前に性能計測の仕組みを入れ、出力を変えない範囲で最適化する

- ステータス: 採用
- 日付: 2026-09-26

## コンテキスト

線数の多い大判図面では、ページの読み込みに十数秒かかることがあります(README「既知の制約」)。サーバーは AWS Lambda(arm64・メモリ 2048MB・タイムアウト 60 秒・応答 6MB 上限)でステートレスに動き(ADR 0019)、同じページを開き直すたびに抽出をやり直します。

高速化・体感改善の案をコードから検討したところ、次のような候補が挙がりました。

- 埋め込み画像の API が、1枚返すたびにページ内の全画像をデコード・PNG 化している(画像数 N に対して N² の処理量)
- 線幅補正がページ全体を 200dpi で描画している(A0 では約 9400×6600 画素)
- 原本画像が 400dpi で描画 → PNG 化 → 応答上限超過なら描き直し、という流れになっている
- 線幅補正の候補選びが、候補の線分ごとに全図形と総当たりで重なりを調べている

しかし、どれが実際の待ち時間やメモリ使用量を支配しているかは測っていませんでした。また、このアプリは抽出結果が元の PDF とどれだけ一致しているかを確かめる用途のため、**UX よりも精度が優先**です。座標の丸め、非可逆な画像形式、結果が変わりうるキャッシュのように、速くなる代わりに出力が変わる手段は採れません。

## 決定

最適化に先立って、次の計測の仕組みを入れます。計測は処理内容と出力を一切変えません。

1. **処理区間の計測(`src/pdf_unit/timing.py`)**: `contextvars` で1リクエスト分の収集器を持ち、`stage(name)` で区間の所要時間を、`metric(name, value)` で件数・画素数などを記録します。区間名は `calib.render` のように `.` で内訳を表します。収集器が無いとき(関数を単体で呼ぶとき)は何もしません。
2. **API の応答ヘッダー**: 各 API は区間の所要時間を `Server-Timing`、件数などを `X-Perf-Metrics`(JSON)で返します。
3. **構造化ログ**: HTTP ミドルウェアが API リクエストごとに、全体の所要時間・リクエスト/応答のバイト数・区間の内訳・件数・コールドスタートかどうか・メモリ(`ru_maxrss`、Linux では現在の RSS も)を1行の JSON で標準出力に書きます。
4. **オフライン計測スクリプト(`scripts/profile_pages.py`)**: PDF のページごとに、各 API を子プロセスで1回ずつ呼び、所要時間・内訳・応答サイズ・ピークメモリを集計します。ページの切り出しは UI と同じ pdf-lib(Node.js)で行います。応答ボディを保存して、変更前後で出力が同一かを確かめられます。
5. **フロントエンドの計測**: API 呼び出しの所要時間・サイズ・`Server-Timing` と、ページ切替からの経過(線データ受信・描画準備完了・初回描画完了・原本画像表示)を `console.debug` に出します。

以降の高速化は、この計測で支配的と分かった箇所から、**出力がバイト単位で同一であることを確認できる変更**に限って行います。

## 理由

- **推測で最適化しない**: 候補はいずれも「重そう」という読みにもとづくもので、効果の大きさの順序が分かりません。計測を先に入れることで、効果の大きいものから手を付けられ、改善の前後を数値で比べられます。
- **`Server-Timing` ヘッダー**: ブラウザの DevTools(Network の Timing)でそのまま見られ、追加の仕組みなしにローカルと Lambda の両方で使えます。
- **1行 JSON のログ**: Lambda では標準出力が CloudWatch Logs に入るため、Logs Insights でそのまま集計できます。コールドスタートの影響も判定できます。
- **子プロセスでの計測**: PDFium のメモリ確保は Python の外(ネイティブ)で行われるため、`tracemalloc` では捉えられません。1回の呼び出しごとにプロセスを分けると、`ru_maxrss` をその呼び出しのピークメモリとして扱えます。Lambda はメモリ上限があるため、時間と同じくピークメモリも判断材料にします。
- **ASGI アプリを直接呼ぶ**: 関数を直接呼ぶ方法では、リクエストの検証や JSON 直列化(`jsonable_encoder` を含む)の時間が抜け落ちます。ASGI アプリに直接 POST を送れば、実際のサーバーと同じ経路を、HTTP クライアント(httpx)を依存に加えずに計測できます。
- **pdf-lib による切り出し**: UI が送るバイト列と同じものを計測するためです。Node.js が無い環境では pypdfium2 で切り出します(バイト列が異なるので、計測値の比較には注意が必要です)。

### 採らなかった案

- **推測にもとづく最適化から着手する**: 上記のとおり、優先度と効果を判断できないため見送りました。
- **`tracemalloc` だけでメモリを測る**: PDFium の描画・デコードのメモリが含まれないため見送りました。
- **Lambda 上での計測から始める**: 本番(`main`)への反映が必要になるため、まずローカルで計測します。ログの形式は Lambda でもそのまま使えるようにしてあります。

## 影響

- API の応答に `Server-Timing` と `X-Perf-Metrics` ヘッダーが加わります。応答ボディは変わりません。`scripts/profile_pages.py --dump` で変更前後の応答ボディを保存して比べ、全件がバイト単位で一致することを確認しました。比べたのは実際の図面 PDF 3種の計10ページ分、105件の応答です(cid 文字を含む A1 判の大判図面1ページ、軽量な図面5ページ、埋め込み画像61枚を含むページを含む4ページ。原本画像は 100/200/400dpi、埋め込み画像は全件)。
- サーバーの標準出力に、API リクエストごとに1行の JSON ログが出ます。
- `with _pdfium_lock:` は、待ち時間を計る `_pdfium_locked()` に置き換えました。ロックの対象と範囲は変わりません(ADR 0011)。
- 計測自体のオーバーヘッドは、区間の出入りでの `time.perf_counter()` の呼び出し程度です。
- 以降の高速化の ADR では、計測結果と、出力が同一であることの確認方法を記録します。
