# ADR 0020: PDF全体ではなく、必要なページだけを切り出して送る

- ステータス: 採用([0019](0019-aws-deployment.md) のPDF全体の送信と、PDF全体の4MB上限を置き換え)
- 日付: 2026-09-25

## コンテキスト

[0019](0019-aws-deployment.md) のステートレス化では、UI が全APIの呼び出しごとに PDF 全体を POST していた。Lambda の同期呼び出しの上限(6MB、関数URLの base64 化で生バイト約4.5MB)に収めるため、PDF全体に 4MB の上限を設けていた。

ユーザーから「PDF 自体はフロントで保持し、抽出が必要なページだけリクエストするのだから、上限の規制は不要ではないか」と指摘された。実際、サーバーは要求ごとに1ページ(サムネイルでも最大10ページ)しか処理しておらず、残りのページを送る必要は無かった。108ページ・36MB の図面は、4MB の上限のため開けなかった。

## 決定

- UI で [pdf-lib](https://github.com/Hopding/pdf-lib) 1.17.1(MIT)を使い、開いたPDFから対象ページだけの PDF を `copyPages` で作って送る。そのページが参照するフォント・画像と、親から引き継ぐ属性(Resources・MediaBox・CropBox・Rotate)だけが入る
  - `/api/page/lines`・`/api/page/image`・`/api/page/images/{k}` は1ページのPDFを受け取り、先頭ページを処理する(URLからページ番号を外した)
  - `/api/thumbs` は最大10ページのPDFを受け取り、その全ページを描画する(`start`/`count` を廃止)。切り出したPDFが送信上限を超えたら半分ずつに分けて送り直し、1ページでも超える場合はそのサムネイルを「表示できません」と表示する
  - `/api/documents/info` は廃止した
- pdf-lib は CDN から読まず、`static/vendor/pdf-lib.min.js` に同梱する(版を固定し、オフラインのローカル利用と AWS 上の両方で同じものを使うため)
  - `index.html` からは相対パス `vendor/pdf-lib.min.js` で参照する。`index.html` と `vendor/` を並べて配置すればそのまま動くので、配信のための設定を環境ごとに持たずに済む(デプロイが1つで済む)
  - ローカルのサーバーは `static/vendor/` を `/vendor` にマウントして配信する
- ページ寸法(サムネイルの枠・図面の枠)は UI が pdf-lib で求める。定義は pdfplumber の `page.width/height` に合わせ、CropBox(無ければ MediaBox)の幅・高さを、`/Rotate` が 90/270 なら入れ替える。`/api/page/lines` はページ寸法も返し、UI の値と食い違えばサーバーの値に合わせる(座標系の基準はサーバー)
- 1ページ分の切り出し結果(バイト列と SHA-256)は直近6ページ分をキャッシュし、同じページの線データ・原本画像(解像度の段階ごと)・埋め込み画像の要求で使い回す
- 送信上限 4MB は「1回に送るPDF」に対してだけかける。UI は超過するページを送らずに「このページはデータが大きく(N MB、上限4MB)処理できません」と表示する。PDF全体の大きさの上限は削除した
- pdf-lib で読めないPDF(暗号化など)は開く時点でエラーを表示する

## 理由

- 必要なページだけを送れば、要求ごとの送信量がページ1枚分になり、PDF全体の大きさに依存しなくなる。Lambda の上限はページ単位で効くだけになる
- 切り出しは速い(108ページ・36MB の図面で読み込み約70ms、1ページの切り出し約2ms)。1ページのPDFは最大1.64MBだった
- 切り出しで抽出結果が変わらないことを確認した。108ページの図面(`/Rotate 90/270` を含む)の全ページ、回転90°のグリフ番号フォントの図面、PDFTron 製の図面、参考図面、埋め込み画像のテストPDF(回転90/270°を含む)の計116ページで、元PDFのページと切り出したPDFの先頭ページについて、ページ寸法・線・文字・埋め込み画像・線幅補正係数がすべて一致した。pdf-lib で求めた寸法も pdfplumber と一致した
- サムネイル・ページ寸法をブラウザ内の描画(pdf.js 等)に移す案もあったが、PDFium による描画をサーバーに残せば表示の一貫性が保て、追加するライブラリも pdf-lib だけで済む

## 影響

- 108ページ・36MB の図面が開けるようになった。ヘッドレス Chrome での確認では、1回の送信は最大3.16MB(サムネイル10ページ分)、53ページ目の件数は元PDFからの抽出と一致した
- 複数ページで共有されるフォント・画像は、切り出したページPDFごとに含まれる。サムネイルのバッチでも同様で、ページ数の割に大きくなることがある
- 1ページだけで 4MB を超えるページ(大きなスキャン画像を含むページなど)は処理できない
- UI に pdf-lib(約0.5MB)の読み込みが加わる
- 開いた PDF 全体(`PDFDocument`)をブラウザのメモリに保持する
