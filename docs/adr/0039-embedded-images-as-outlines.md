# ADR 0039: 埋め込み画像は画像データを取得せず、枠と原本画像で表示する

- ステータス: 採用([0010](0010-embedded-raster-images.md) の画像データの再描画を置き換え。UI は [0026](0026-embedded-image-png-on-demand.md)・[0032](0032-embedded-images-batch-api.md) の API を使わなくなった)
- 日付: 2026-09-26
- 追記(2026-09-26): [0040](0040-remove-embedded-image-data-api.md) で、使われなくなった `/api/page/images/{k}`・`/api/page/images` を削除しました。

## コンテキスト

約100ページのPDFでp74を開くと、`/api/page/images/{k}` へのリクエストが約600本飛び、なかなか読み込みが終わらないと報告されました。

原因は次のとおりです。

- UI は線データを受け取ると、ページ内の埋め込み画像1枚ごとに `/api/page/images/{k}` を一度に要求していた。同時に投げる数の上限はなく、ページを切り替えても取り消さなかった
- サーバーは1回ごとにPDFを開き直し、画像番号を安定させるため全画像をデコードしてから1枚を PNG 化する(ADR 0026)。画像 N 枚のページではデコードが N² 回になる。ローカルでは PDFium のロックで直列に処理され、ブラウザも同じホストへの同時接続数の上限で待たされる
- 合成PDF(32×32画素の画像を並べたもの)では、1枚ずつの要求の合計が 100枚で約0.5秒、600枚で約16.6秒だった。まとめ取得 API(ADR 0032)なら 600枚でも 76ms。移行前(pdfplumber 版)も 600枚で約18.6秒で、ADR 0038 の移行による悪化ではない
- 画像が多いのは、PDF 内で1枚の絵が帯状の多数の画像に分けて保存されているためと考えられる(埋め込み画像61枚のページは、1312×24画素の JPEG の帯が0.1pt強ずつ重なって並んでいた)。実装が分割しているのではない

UI は画像データを配置位置に描き直していました(ADR 0010)。しかし、元の PDF との照合という用途では、画像の絵柄は下敷きの原本画像にも写っています。ユーザーの判断で、画像データの取得をやめ、配置範囲の枠を描くことにしました。そのうえで、原本画像の濃さを下げると絵柄が見えなくなるため、画像の範囲だけは原本画像を不透明で見せることにしました。

## 決定

- UI は埋め込み画像の画像データを要求しない。`/api/page/lines` が返す配置範囲(`quad`)に枠(凡例の image の色 `#64748b`、線幅1px)を描く
- 枠の中は、原本画像の濃さの設定によらず、原本画像を不透明で描き写す。全画像の範囲を1つの `Path2D` にまとめて Canvas をクリップし、原本画像を1回だけ描く(`render/draw.ts` の `drawOriginalIn`)。選択中は、ほかの要素と同じく減光し、選ばれた画像は減光前の濃さで描き直す。原本画像の読み込みが終わったら描き直す
- ページや文書を切り替えたら、前のページの `/api/page/lines`・`/api/page/image` の要求を `AbortController` で取り消す(取り消した要求のエラーは表示しない)
- サーバーの `/api/page/images/{k}`・`/api/page/images` は残す(UI からは使わない)
- E2E の並走比較(ADR 0031)では、旧UIとの差として意図したものを比較から外す。画素の比較では画像の範囲をマスクし、通信の比較では `/api/page/images` を除く

## 理由

- 画像のリクエストが0本になるので、画像の多いページでもサーバーと通信の負荷が増えない。まとめ取得 API に切り替える案もあったが、画像データを取得しなければ、そもそも待ち時間も負荷も生じない
- 絵柄は原本画像そのもの(PDFium の描画)なので、画像データを再描画するより元の PDF に忠実です。透過マスクや回転したフォーム内の画像など、再描画では再現しきれなかった見た目の問題(ADR 0010 の既知の制約)もなくなる
- 範囲の中だけ不透明にするので、原本画像の濃さを下げて線を見比べる使い方と両立する
- 取り消しは UI だけの変更で、古い応答はもともと要求番号で捨てていた(状態は変わらない)。取り消すことで、ブラウザの接続と応答の受信・解析を無駄にしない

### 採らなかった案

- **まとめ取得 API(ADR 0032)に切り替えて画像データを描き続ける**: 要求は数本に減るが、ユーザーの判断で枠の表示を選んだ
- **フロントだけで画像データをデコードする**: pdf-lib には JPEG 以外(JPEG2000・CCITT・JBIG2・索引色・CMYK・透過マスク等)のデコード機能が無く、pdf.js のような PDF エンジンを足す必要があるため見送った

## 影響

- 「ラスター」表示と image の凡例は、絵柄の再描画ではなく枠と原本画像になる。画像の属性(画素数・解像度・圧縮形式)、ホバー・クリックは変わらない
- 原本画像の読み込み前は枠だけが見える。原本画像は解像度段階(100/200/400dpi)で取り直すため、拡大直後は粗い絵柄になりうる(下敷きと同じ)
- サーバーの API と応答は変わらない
