# ADR 0024: API の応答を gzip で圧縮し、Lambda の応答上限に収める

- ステータス: 採用
- 日付: 2026-09-26

## コンテキスト

ADR 0023 の計測の仕組みで、実際の図面 PDF 3種(cid 文字を含む A1 判の図面1ページ、軽量な図面70ページ、埋め込み画像を含む図面47ページ)を計測しました。その結果、`/api/page/lines` の応答(JSON)が Lambda の応答上限 6MB を超えるページが、計測できた114ページ中8ページありました(1/1、5/67、2/46。最大 12.8MB)。線の数が多いページ(A1 判で約4.7万本)が該当します。本番(CloudFront → Lambda 関数URL、BUFFERED)ではこれらのページを表示できません。

応答の内訳は線データが大半で、`polylines`・`bbox`・`d` が主です。JSON の数値の繰り返しが多いため、よく圧縮できます(12.8MB が gzip で約2MB)。一方、現状は次の理由で圧縮されていませんでした。

- CloudFront の `/api/*` はキャッシュ無効(`CachingDisabled`)のキャッシュポリシーで、CloudFront の自動圧縮が効いていない
- アプリ側にも圧縮の仕組みが無い

## 決定

- FastAPI(Starlette)の `GZipMiddleware` を追加し、ブラウザが `Accept-Encoding: gzip` を送ってきた場合に応答を gzip で圧縮します。圧縮レベルは4にします。
- ミドルウェアは計測ログのミドルウェアより内側に置き、ログの `resp_bytes` を圧縮後(転送される)大きさにします。
- `scripts/smoke_test.sh` に、`Accept-Encoding: gzip` を付けた `POST /api/page/image` が gzip で返ることの確認を加えます。本番では CloudFront と Lambda Web Adapter を通っても圧縮が効いていることを、デプロイのたびに確かめます。
- `scripts/profile_pages.py` もブラウザと同じく `Accept-Encoding: gzip` を付けて送ります。展開後の大きさ(`resp_bytes`)、転送される大きさ(`wire_bytes`)、Lambda の上限と比べる大きさの推定(`lambda_bytes`)を記録します。`--dump` には展開後のボディを保存するので、出力の比較方法は変わりません。

## 理由

- **精度を落とさない**: gzip は可逆圧縮で、ブラウザが展開するため、UI が受け取る内容は変更前とバイト単位で同じです(ADR 0023 の方針)。
- **上限に収まる**: 圧縮した応答は Lambda Web Adapter が base64 にして返すため、Lambda の上限と比べる大きさは圧縮後の約4/3倍です。計測で最大だった 12.8MB の応答は、圧縮レベル4で 2.14MB、base64 にしても約2.85MB になります。3種の PDF の全ページで、上限の半分以下に収まることを確認しました。
- **圧縮レベルを4にした理由**: 12.8MB の応答で比べると、既定の9は 1.95MB・760ms、6は 1.97MB・239ms、4は 2.14MB・87ms、1は 2.58MB・52ms でした。9は時間がかかる割に縮まらないため、上限までの余裕と時間の釣り合いから4にしました。
- **CloudFront を通しても効く**: CloudFront は、ビューアーの `Accept-Encoding` に gzip が含まれていれば、正規化した `Accept-Encoding` をオリジンに転送します(AWS のドキュメント「Request and response behavior for custom origins」)。オリジンが gzip で返した応答はそのままビューアーに届きます。念のため smoke test でも確かめます。
- **転送量も減る**: 原本画像や埋め込み画像(PNG の base64)も3割程度縮みます。

### 採らなかった案

- **応答ストリーミング(関数URLの `RESPONSE_STREAM`)**: 上限は緩みます(20MB)が、infra の変更が必要で、アプリ側だけで完結しません。gzip で十分に収まるため見送りました。
- **JSON の内容を減らす(座標の桁数を減らす、`d` と `polylines` の二重持ちをやめる)**: 座標の丸めは精度が落ちるため採りません。`d` をクライアントで `polylines` から組み立てる案は、数値の書式(`f"{x:.2f}"` と `round(x, 2)`)の違いで同一の結果になる保証が無いため、見送りました。
- **CloudFront 側で圧縮する**: キャッシュ無効の API で CloudFront の自動圧縮を使うにはキャッシュポリシーの変更が必要で、infra 側の変更になります。アプリ側の圧縮で足りるため見送りました。

## 影響

- 大きな応答では圧縮の時間が加わります(12.8MB で約90ms、手元での計測)。転送量が1/6前後になるため、通信時間はそれ以上に短くなる見込みです。
- 応答の `Content-Length` は圧縮後の大きさになります。UI のコンソールの計測ログ(ADR 0023)の「受信」も圧縮後の値です。
- 1ページの切り出しが 4MB を超える場合の送信側の上限(Lambda のリクエスト上限による)は、この変更では解消しません。3種の PDF では4ページが該当しました。
- 検証として、変更前後で全 API の応答ボディ(展開後)105件がバイト単位で一致することを `scripts/profile_pages.py --dump` で確認しました(ADR 0023 と同じページ)。
