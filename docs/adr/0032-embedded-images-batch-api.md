# ADR 0032: 埋め込み画像をまとめて返す API を追加する

- ステータス: 採用(サーバー側。UI からの利用は Issue #9 で対応)
- 日付: 2026-09-26
- 追記(2026-09-26): [0039](0039-embedded-images-as-outlines.md) で、UI は埋め込み画像の画像データを取得しなくなったため、この API も UI からは使っていません。API は残しています。
- 追記(2026-09-26): [0040](0040-remove-embedded-image-data-api.md) でこの API(`/api/page/images`)を削除しました。

## コンテキスト

UI は `/api/page/lines` の応答に含まれる埋め込み画像の数だけ `/api/page/images/{k}` を同時に要求します(ADR 0010)。サーバーはステートレスなので、1回ごとにページ全体を走査し、全画像の画像データを取り出します。画像番号を保つため、取り出しは要求された画像以外にも行います(ADR 0026)。そのため、画像 N 枚のページを表示すると処理量は N² に比例します。

調査(Issue #8・#9)で、実際の図面には埋め込み画像が数千〜1万枚を超えるページがあると分かりました。こうしたページには次の問題があります。

- 画像の要求が数千回同時に発生し、Lambda の同時実行数の上限(本番アカウントで1,000)を超える
- 処理量は、手元の計測で次のとおり
  - 2,073枚のページ: 1枚あたり約0.25秒、全画像で推定約520秒
  - 11,664枚のページ: 1枚あたり約0.6秒、全画像で推定約2時間
  - Lambda は手元より約3.3倍遅いため、予算(月3USD)の面でも無視できない

## 決定

- `POST /api/page/images?start=&count=` を追加します。
  - 1回のページ走査で、画像番号 `start` から最大 `count` 枚(既定100、上限500)を PNG 化して返します。
  - base64 の合計が応答上限(5.5MB、`MAX_PNG_BASE64_CHARS`)に収まるところで区切ります。1枚目は必ず含めます(1枚ずつは縮小処理で上限内に収まっています)。
  - 応答は `{images: [{index, png_base64}], total, next}` です。`next` は続きの画像番号で、無ければ `null` です。
- 各画像の `png_base64` は `/api/page/images/{k}` と同じ処理(`_downscale_png`)で作ります。
- 既存の `/api/page/images/{k}` はそのまま残します。

## 理由

- **処理量が N² から N になる**: 1回の走査で多くの画像を返すので、ページ全体の走査回数は `N / count` 回程度になります。手元の計測では次のとおりです。
  - 61枚のページ: 1枚ずつの合計 約1.5秒 → まとめ取得1回 0.08秒
  - 2,073枚のページ: 推定 約520秒 → まとめ取得21回で 約5秒
  - 11,664枚のページ: 推定 約7,000秒 → まとめ取得117回で 約69秒
- **同時要求数が減る**: 1ページあたりの要求が数回〜数十回になり、Lambda の同時実行数の上限に達しにくくなります。
- **出力を変えない**: 返す PNG は1枚ずつの API と同じ関数で作るので、バイト単位で同じです(ADR 0023 の方針)。検証として、61枚のページでは全画像、2,073枚と11,664枚のページでは抜き取った画像(43枚・60枚)が、1枚ずつの API とバイト単位で一致することを確かめました。全画像が漏れなく取得できることも確かめました。
- **応答上限の守り方**: 画像ごとの上限は既存の縮小処理で守られています。まとめたときの合計が上限を超えないよう、合計で区切ります。

### 採らなかった案

- **1回の要求で全画像を返す**: 応答上限(6MB)を超えるページがあるため、区切りと続きの取得が必要です。
- **サーバーで画像データを保持して再利用する**: サーバーはステートレスの方針(ADR 0019)で、キャッシュは結果が変わりうるため採りません。
- **UI の同時要求数だけを制限する**: 同時実行数の問題は緩和できますが、処理量が N² であることは変わりません。

## 影響

- UI がこの API を使うまでは、挙動は変わりません(Issue #9)。まとめ取得へ移行するまでのつなぎとして、UI 側で同時要求数を制限する案も Issue に残しています。
- 1回の要求は、1枚ずつの要求より時間がかかります(11,664枚のページで1回あたり約0.6秒、Lambda では約2秒の見込み)。UI は区切りごとに順次または少数並列で要求し、届いた分から表示できます。
- 取り出し(`get_bitmap`)は、画像番号を保つため毎回全画像で行います(ADR 0026)。まとめ取得の回数が多いページでは、この取り出しが残りの時間の大半になります。
