# ADR 0048: サムネイルを描いたページは pdf.js の後始末(`page.cleanup()`)を呼んで捨てる

- ステータス: 採用
- 日付: 2026-10-01

## コンテキスト

「長時間ブラウザで開いているとPCが重くなる」という報告を受け、大きいPDFを開いたときのメモリを計測した。

計測には合成PDFを使った。73MB・30ページで、各ページに線2万本(水平・垂直が8割、短い斜線が2割)と 1800×1200 の画像1枚を含む。Chromium(Playwright)・DPR 2 で開き、全ページのサムネイルが描き終わった後に GC してから測った。Worker の JS ヒープ(ArrayBuffer・Blink 側のオブジェクトを含む)は 565MB、レンダラープロセスの RSS は 1.98GB だった。何も操作していない間も、レンダラーは10秒あたり約1.4秒の CPU を使い続けていた(大きなヒープに対する GC が繰り返されるため)。

Worker のヒープスナップショットを見ると、`Path2D` が60万個(30ページ×2万本)で 334MB を占めていた。ほかに、その座標の `Float32Array`・`ArrayBuffer` もあった。pdf.js 6 は、ページの描画命令列(operator list)に `Path2D` を作って持たせる。この命令列とページ内の画像(`page.objs`)は、`PDFPageProxy.cleanup()` を呼ぶまで保持され続ける。`doc.getPage()` のページもキャッシュされるため、先読みで全ページを描くと、全ページ分の命令列が Worker に溜まっていく。

[0042](0042-thumbnail-prefetch-all-pages.md) では「Worker 内は1ページずつ直列に処理するので、メモリは1ページ分の作業領域に収まる」としていた。しかし実際に一定だったのは同時に描く枚数だけで、描き終えたページの資源は残り続けていた。

## 決定

- `thumbnail-worker.ts` の `handleRender` で、ページを描き終えたら(失敗した場合も)`page.cleanup()` を呼ぶ
- 文書全体の `doc.cleanup()`(フォント・複数ページで共有する画像のキャッシュ)は呼ばない。描画中に呼ぶと描画が壊れうるため。文書ごとの資源は、先読みが終わった時点で文書ごと閉じて解放する([0050](0050-close-thumbnail-document-after-prefetch.md))

## 理由

- 同じ文書で同じページを描き直すことはない。1ページにつき要求は1回で、成功しても失敗しても再要求しないため、描き終えたページの命令列・画像を残す意味がない
- `cleanup()` は描き終えた資源を捨てるだけで、描画結果は変わらない。合成PDF 30ページのサムネイル(PNG)は、変更前後でバイト列が一致した

## 影響

- 同じ合成PDFで、Worker のヒープは 565MB から 79MB、レンダラーの RSS は 1.98GB から 0.70GB になった。操作していない間の CPU 使用はほぼ0になった。先読みの所要時間も少し短くなった(CPU 時間 8.2秒 → 6.1秒)
- [0042](0042-thumbnail-prefetch-all-pages.md) のメモリに関する記述はこの ADR で訂正した(0042 に追記した)
