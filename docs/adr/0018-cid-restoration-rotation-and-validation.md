# ADR 0018: cid 文字の補完はページ回転を反映して突き合わせ、根拠の無い推測はせず「□」で示す

- ステータス: 採用([0009](0009-cid-character-restoration.md) の一部を置き換え)
- 日付: 2026-09-25

## コンテキスト

最新の図面(47ページ)で、再びテキストが `(cid:N)` と表示された。調査の結果、原因は次の3点だった。

1. **ページ回転を考慮していなかった**: この図面は `/Rotate 90`。PDFium の文字原点は回転前のPDF座標(例: 565.9, 510.1)、pdfplumber の文字位置は回転後の座標(510.1, 29.1)のため、[0009](0009-cid-character-restoration.md) の突き合わせが1件も成立していなかった
2. **判定に抜け穴があった**: 0009 は「PDFium の結果が chr(CID) と一致すれば、そのフォントは CID=Unicode」とみなしていた。しかし PDFium も対応が分からないときは CID をそのまま Unicode として返すため(この図面では `㸫ග…` のような化け文字)、一致は根拠にならない。突き合わせが成立していれば、化け文字を正しい文字として表示していた
3. **そもそも復元の情報が無い**: フォントはＭＳゴシックの部分埋め込み(`CIDFontType2`、`Identity-H`、`CIDToGIDMap = Identity`)で、ToUnicode が無く、埋め込みフォントからも `cmap`・`post`・`name` テーブルが削られていた。CID は元フォントのグリフ番号(部分フォントのグリフ数 22,291 のうち実体は161)で、PDF の中には何の文字かを示す情報が無い

## 決定

- PDFium の文字原点を、埋め込み画像と同じ `PageToDisplay`(`FPDF_PageToDevice`、[0010](0010-embedded-raster-images.md))で表示座標へ変換してから突き合わせる。pdfplumber 側は `matrix` の (e, f) を上原点 (e, 高さ − f) に直す
- PDFium の結果は、chr(CID) と**異なる**場合だけ採用する(PDFium がフォント内部の情報から実際に対応を見つけた場合)
- chr(CID) と同じ結果や突き合わせられなかった文字は、フォント単位でまとめて判定する。chr(CID) の9割以上が「よく使われる文字の範囲」(ASCII・ラテン・ギリシャ・キリル・一般記号・かな・CJK統合漢字・ハングル・全角形など)に収まる場合だけ、CID=Unicode のフォントとみなして chr(CID) を使う
- どちらでも決まらない文字は「□」で表示し、文字に `unreadable` フラグを付ける。単語ごとに数を数えて、属性パネルに「読めない文字: N字」と表示する(本物の「□」と区別するため、表示文字だけで判定しない)

## 理由

- 座標系の違いは埋め込み画像で既に解決済みの問題で、同じ変換を使えば回転ページでも pdfplumber と一致する
- 化け文字を正しい文字として出すと利用者が誤りに気付けない。復元できないことを明示する方が安全
- CID=Unicode のフォント(PDFTron 製の図面)は、使われる文字がかな・漢字・全角英数などに集中する。グリフ番号を文字とみなすと、シンハラ文字や拡張漢字など無関係な範囲に散らばるので、分布で見分けられる

## 影響

- 今回の図面: 化け文字も `(cid:N)` も出なくなり、復元できない文字は「□」で表示される(1ページ目は1,219文字中1,216文字)
- PDFTron 製の図面(CID=Unicode): 従来どおり2,235語すべて復元される。参考図面・108ページの図面は変化なし
- 今回のようなフォントを復元するには、同じ版の元フォント(Windows の `msgothic.ttc` 等)の cmap でグリフ番号から文字を引く方法がある。版違いによるずれを防ぐため、元フォントのグリフ形状との照合も必要になる(未実装)
