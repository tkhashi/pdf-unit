# ADR 0037: pdfplumber → pypdfium2 移行の技術調査の結果と移行案

- ステータス: 提案
- 日付: 2026-09-26

## コンテキスト

ADR 0036 の判定を受けて、移行が可能かどうかの技術調査を行いました。調査の途中で ADR 0036 を見直したところ、次の誤りが見つかりました。ADR 0036 は上書きせず、ここで訂正します。

- **座標の一致を実PDFで確かめていなかった**: 「出力(座標・分類・線幅・色)も実PDFで高い一致率を確認できました」と書きましたが、実PDFで比べたのは件数だけでした。座標まで比べたのは合成PDF1枚だけです。
- **速度比の比べ方が公平でなかった**: 線の PoC はヒット判定用の `polylines` を作っていませんでした。また、本番の `/api/page/lines` では pdfminer の解析を線とテキストで1回だけ共有しています。線とテキストの速度比を別々に出すと、この解析時間を二重に数えることになります。
- **画像化の速度とメモリの記述が誤っていた**: 「画像化は 0.53〜0.76 倍」「400dpi で PoC 側のメモリが大きい(1040MB→1500MB)」と書きましたが、計測スクリプトで pdfplumber 側だけ `import pdfplumber` が計測区間に入っていたこと、PNG の保存まで含めて計っていたことによるものでした。正しく計り直した結果は下記のとおりです(差は 2〜6%、メモリは同等)。
- 大判図面を「A0 判」と書きましたが、2384×1684pt なので A1 判です。

計測にはいずれも、ADR 0036 と同じ実際の図面 PDF を使いました(ファイル名は記録しません)。以下では次の呼び方をします。

- **PDF-A**: cid 文字を含む A1 判の大判図面1ページ(図形 46800 個、単語 2235 語)
- **PDF-B**: 軽量な図面(70ページ中57ページが90°回転)。1〜5ページを計測
- **PDF-C**: 埋め込み画像 61 枚を含むページ(90°回転、Separation 色空間、ToUnicode の無いフォント)

## 調査の方法

1. **互換クラス(`scripts/poc_pypdfium2/pdfium_page.py` の `PdfiumPage`)**: 既存の `extract_page_lines`・`calibrate_linewidth`・`extract_page_texts` は、pdfplumber の Page から `width`・`height`・`rects`・`curves`・`lines`・`chars`・`to_image()` だけを読みます。これらを PDFium から pdfminer/pdfplumber と同じ規則で組み立てるクラスを作り、**既存の関数を改造せずに**渡しました。再現した規則は次のとおりです。
   - 座標: MediaBox と /Rotate から pdfminer と同じページ行列を作り、pdfplumber の `point2coord`・`top`/`bottom` の式で上原点に直す
   - 図形: サブパスごとに分け、`ml`/`mlh` は line、軸に平行な閉じた4辺は rect、それ以外は curve にする(pdfminer の `paint_path`)。PDFium が閉路に足す「始点へ戻る点」は取り除く
   - 線幅: `w` の値に CTM の拡大率を掛ける(pdfminer の `do_w`)
   - 文字: (0, descent)〜(送り幅, descent+フォントサイズ) の矩形を文字行列で写す(pdfminer の `LTChar`)
   - 数値: PDFium の API は float32 を返すため、「float32 として同じ値になる最短の10進数」に戻してから pdfminer と同じ順序で行列を掛ける
2. **応答全体の比較(`scripts/poc_compare.py`)**: `/api/page/lines` の応答を、本番(`server.page_lines`)と `PdfiumPage` で作って突き合わせます。線は要素ごとにキー単位で比べ、テキストは文字の原点の位置と単語の文字列で対応づけて比べます。時間は子プロセスで3回計り最小値を採り、本番と同じ区間名で内訳を出します。
3. **合成PDF(`scripts/poc_pypdfium2/fixtures.py`)**: 実PDFはリポジトリに置けないため、差が出うる条件(ページ回転・MediaBox の原点・CropBox・複数サブパス・`v`/`y` 演算子・色空間・Form XObject・拡大したテキスト・CTM での線幅)を1ページずつ作りました。
4. **同時リクエスト(`scripts/poc_pypdfium2/concurrency.py`)**: ページ切替時の3リクエスト(線データ+原本画像2解像度)を1プロセスで同時に投げて計ります。

## 結果

### 処理時間(`/api/page/lines` 全体、手元の Apple Silicon)

| PDF | pdfplumber | pypdfium2 | 比 | 主な内訳(pdfplumber → pypdfium2) |
| --- | --- | --- | --- | --- |
| PDF-A | 4765ms | 1468ms | 0.31 | 解析 4012→710ms、線の整形 374→351ms、テキスト 130→87ms、画像 139→139ms |
| PDF-B 1〜5ページ | 61〜215ms | 32〜145ms | 0.52〜0.91 | 解析 48〜149→14〜22ms。文字の読み取りが 50〜80ms 増える |
| PDF-C | 109ms | 64ms | 0.59 | 解析 70→20ms |

- 短縮の大半は pdfminer による解析をなくしたことによります。線の整形(既存の `extract_page_lines`、純 Python)は変わらないため、移行後は PDF-A でこれが全体の約1/4を占めます。
- 文字の読み取りは、ctypes で1文字ずつ約12回 API を呼ぶため、1文字あたり約10µs かかります(約6000文字のページで 50〜80ms)。PDF-B の5ページ目は、この区間のばらつきで比が 0.91 になりました。
- float32 から10進数への復元には、PDF-A で約 100ms かかります(キャッシュ込み)。

**原本画像(`/api/page/image`)**: PDFium で直接描画しても、base64 の PNG は3種・100/400dpi のすべてで SHA-256 まで一致しました。時間は 0.94〜0.99 倍(5回の最小値)、ピークメモリは同等でした(PDF-A 400dpi で 1108MB と 1106MB)。

**同時リクエスト**: 移行すると線データの処理がすべて `_pdfium_lock` の中に入り、原本画像の描画と直列になります。それでも線データの応答は早くなりました(PDF-A 4761→1448ms、PDF-B 3ページ目 254→141ms、PDF-C 161→65ms。3リクエスト全体は同等か短い)。なお、Lambda は1つの実行環境で同時に1リクエストしか処理しません(infra の Lambda 定義は通常の関数で、同時実行を増やす設定はありません)。本番ではロックの取り合い自体が起きず、影響はローカルの開発サーバーに限られます。

### 出力の一致

**線(`lines`)**

- PDF-B の5ページ(8272個)は、**応答の線がバイト単位ですべて一致**しました。PDF-A も 46800 個すべてで、線幅以外(`type`・`d`・`polylines`・`color`・`bbox`)が一致しました。
- float32 のまま使うと、すべての線が一致しなくなります(`bbox` に 3e-5pt 程度、線幅に 3e-8 程度の差)。10進数への復元は必須です。
- 合成PDFでは、基本図形・複数サブパス・CTM での線幅・90°/270°回転・MediaBox の原点・CropBox・`q`/`Q` で囲んだ Form XObject のすべてで一致しました。
- 一致しなかったもの:
  - **線幅**: PDF-A では 46566 個が異なります。pdfminer は `w` を実行した時点の CTM で線幅をスケールし、PDFium は描画時の CTM での太さになります。PDF-A は線幅を mm 単位の `w` で設定し、描画時の `cm` で mm→pt に拡大しているため、pdfminer は mm の値(0.09 など)をそのまま報告します。PDFium 側の値(0.2551pt など)が実際の描画の太さと合うことを、400dpi で描画して確かめました(例: 報告 0.09・PDFium 0.2551 の直線が実測 0.36pt=2画素)。約2割の図形では、pdfminer の報告値と実際のペンの対応もずれていました。本番は、この食い違いを `linewidth_scale`(線幅補正)で後から補っています
  - **色**: PDF-C の 1849 個が異なります(下記「既存の不具合」の Separation 色空間)
  - **float32 の精度の限界**: 有効数字8桁以上の値は復元できません(PDF-A のページ幅 `2383.9399` が `2383.94` になる、PDF-C の7個の `bbox` に最大 4.7e-5pt の差)
  - **閉路の表現**: PDF 内に「始点へ戻る `l` と `h`」と書かれた閉路は、PDFium では `h` だけの閉路と区別できず、`d` の重複点が1つ減ります(PDF-C で1個、全体の約5.7万個中1個)

**テキスト(`texts`)**

- 文字単位では、同じ原点にある文字の文字列・サイズ・回転・横倍率・フォント名・色が一致しました(PDF-A で 7484 文字中 7473 文字が同じ原点。PDF-B・C も同様。色は PDF-C の Separation を除く)。cid 文字も PDF-A では両方とも「□」0件でした。
- 単語の文字列の一致: PDF-A 2227/2235 語、PDF-B 36/36・283/283・954/957・1062/1063・1060/1060 語、PDF-C 42/53 語。差の多くは、同じ文字を少しずらして2回描く太字表現(PDFium は重複を1文字にまとめる)によるものです。
- **バイト単位で一致する単語はありません**。文字の上下端を決める descent を、pdfminer はフォント記述子/AFM から、PDFium はフォント実体から取るため、外接矩形がずれます(埋め込みフォントで 0.0002pt 以下、PDF-A の一部フォントで最大 0.27pt、埋め込まれていない標準フォントでは Helvetica 18pt で 0.072pt)。
- **単語の分割は数値のわずかな差に敏感です**。回転した文字では pdfminer の `size` が送り幅方向の長さになり、`extract_words` は `size` が完全に等しい文字しか同じ単語にしません。外接矩形から逆算した送り幅には float32 の誤差が乗るため、そのままでは PDF-A の単語の一致が約92%でした。フォントの幅を 1/1000 em の 0.1 単位に戻して pdfminer と同じ式で作り直すことで、99.6% になりました。PDF 内の /Widths を持たない標準フォントでは PDFium 内蔵のメトリクスが使われ、なお分割が変わることがあります。
- **ToUnicode の無いフォント**: pdfminer は引けない文字を `(cid:N)` にし、本番はそれを手がかりに「□」を付けます(ADR 0009/0018)。PDFium の公開 API には、引けなかったかどうかの区別も CID の値もありません。本番の判定の後半(フォント内の文字がよく使われる文字に9割以上収まらなければ読めないフォントとみなす)をフォント内の全文字に当てはめる近似を試したところ、PDF-C では本番の「□」480文字に対して498文字になりました(差の18文字は、本番が意味のない文字を出している箇所)。PDF-A・B で誤って「□」になった文字はありませんでした。ToUnicode があっても珍しい文字ばかりのフォントは、この近似で誤って「□」になりえます。
- 横方向の拡大(`Tz`)があるテキストでは、pdfminer の文字行列は拡大を含まず、PDFium は含みます。そのため `sx`(横倍率)が変わります(PDFium の値が実際の字形に合います)。

**埋め込み画像(`images`)**: 同じ関数(`extract_page_images`)なので、PDF-C の 61 枚すべてが一致しました。

### PDFium の公開 API では再現できないもの

1. 色: PDFium は RGB に変換済みの整数しか返しません。CMYK は変換式が異なり(例: (0.1, 0.2, 0.3, 0.4) が本番 `rgb(128,102,77)`、PDFium `rgb(150,135,118)`)、RGB でも `round()` の偶数丸めにかかる値(0.3→本番 76、PDFium 77)は変わります。
2. 文字の descent(外接矩形の上下端)
3. ToUnicode の有無と CID の値
4. 有効数字8桁以上の数値(float32)
5. 「始点へ戻る `l` と `h`」の閉路と「`h` だけ」の閉路の区別
6. 太字表現の重複文字(PDFium のテキスト処理がまとめる)

### 本番(pdfminer/pdfplumber)の既存の不具合

調査の中で、移行とは関係なく本番に存在する次の問題が見つかりました。いずれも PDFium 側では起きません。

1. **`v`/`y` 演算子の曲線が崩れる**: pdfminer は `v`/`y` をそのまま残しますが、`extract.py` の `_path_from_commands`・`_flatten_commands` は `m/l/c/h` しか扱わず、形が崩れて `polylines` が空になります。
2. **線幅**: `w` を指定していないパスを 0 と報告します(PDF の仕様の既定値は 1.0)。また、上記のとおり `w` 実行時点の CTM でスケールするため、`w` の後に `cm` があると実際の太さと合いません。
3. **Separation 色空間の色が白になる**: `/CS 1 SCN`(濃度 1.0)を pdfminer は `1.0` とだけ返し、`_color_to_css` がグレーの 1.0 と解釈して `rgb(255,255,255)` にします。PDF-C では線と文字がすべて白と報告されています。
4. **`q`/`Q` で囲まない Form XObject の後の図形**に、Form の行列がかかります(pdfminer がデバイスの CTM を戻さないため)。
5. **CropBox が MediaBox と異なるページ、MediaBox の原点が 0 でないページで、線と原本画像がずれる**: pdfplumber 0.11.10 はページ寸法と座標の原点に MediaBox を使い、PDFium の描画は CropBox の範囲になります。合成PDFで、線の矩形 (80, 90)-(140, 130) が画像上では (43.5, 58.5)-(135, 120) に表示されることを確かめました。UI の `services/pdf.ts` の `pageSize` には「pdfplumber の page.width/height と同じ定義: CropBox」とありますが、実際の pdfplumber は MediaBox を使います。今回の実PDF 3種には該当ページはありませんでした。
6. **ページツリーが壊れたPDF**: pdfminer は /Type /Page を探して1ページと数え、その後の PDFium の呼び出しで `PdfiumError` が捕まえられず、500 になります(合成した0ページのPDFで確認)。

### エラー処理

| 入力 | 本番 | PDFium で開いた場合 |
| --- | --- | --- |
| 途中で切れたPDF・中身が壊れたPDF | 400 | 読み込み失敗(400 にできる) |
| xref が壊れたPDF | 400 | 修復して開ける(一般的なビューアと同じ) |
| ページツリーが壊れたPDF | 500 | 読み込み失敗(400 にできる) |

暗号化PDFは qpdf が無く合成できなかったため、確かめていません(UI の pdf-lib が暗号化PDFを読み込めないため、通常はサーバーに届きません)。`/api/page/images*` は入力の検証のためだけに pdfplumber で PDF を開いているので、移行する場合はここも PDFium に置き換えます。

### 依存と Lambda

- pdfplumber を外すと、pdfminer.six・cryptography・cffi・pycparser・charset-normalizer も不要になります(Linux arm64 の wheel で計 11.9MB)。import の時間は `pdfplumber` 50ms に対して `pypdfium2` 26ms で、コールドスタートへの影響は小さいです。
- pypdfium2 は現在 pdfplumber 経由の推移的な依存です(5.13.0)。移行するなら `pyproject.toml` に直接の依存として固定します。arm64 の wheel はすでに本番の zip に含まれています。
- 単語へのまとめ(`pdfplumber.utils.extract_words`)は純 Python(MIT ライセンス、約1200行)ですが、`pdfplumber.utils` を import すると pdfminer まで読み込まれます。依存を外すには、ライセンス表記を付けて取り込む必要があります。

## 決定(提案)

技術的には移行できます。互換クラスを挟めば、線・線幅補正・テキストの既存の関数をそのまま使え、重いページで約3倍、軽いページで 1.1〜1.9 倍速くなります。ただし、**ADR 0023 の「出力がバイト単位で同一であることを確認できる変更に限る」を満たせません**。変わるのは次の点です。

- 線幅(PDF-A では全図形。実際の描画の太さに合う方向の変化で、`linewidth_scale` も変わる)
- 色(Separation は白→黒に直る。CMYK は変換式が変わる。RGB の丸め境界)
- テキストの外接矩形(全単語、最大 0.27pt)、単語の分割(0.4〜4%)、ToUnicode の無いフォントの判定(近似)
- `v`/`y` の曲線、`q`/`Q` の無い Form の後の図形(いずれも正しくなる方向)

速度の改善は pdfminer の解析をなくすことで得られます。この解析は線とテキストで共有しているため、線だけを移しても解析は残り、ほとんど速くなりません。**改善を得るには、テキストの出力の変化を受け入れる必要があります**。この判断はユーザーに委ねます。進める場合は、次の順で段階的に移行することを提案します。

1. `scripts/poc_pypdfium2/fixtures.py` と `scripts/poc_compare.py` を回帰テストとして整備する
2. 原本画像(`_render_page`)と `/api/page/images*` の検証を PDFium に置き換える(出力はバイト単位で同一。速度の差はほぼ無いが、pdfplumber への依存を減らせる)
3. 線データを `PdfiumPage` 相当の互換層に置き換え、1つの PDFium ドキュメントで線・線幅補正・テキスト・埋め込み画像を処理する。上記の出力の変化を新しい ADR に仕様変更として記録し、README を更新する
4. pdfplumber を依存から外し、`extract_words` を取り込み、pypdfium2 を直接の依存として固定する

移行しない場合も、上記「本番の既存の不具合」は別途直す価値があります(特に Separation の白、`v`/`y` の曲線、CropBox のずれ)。

### 採らなかった案

- **線だけ・画像だけを移す**: 解析が残るため速度の改善がほとんど無く、依存も減りません。
- **PDF のコンテンツストリームを自前で解析して色や CID を取る**: pdfminer と同じ量の Python の処理が必要になり、速度の改善がなくなります。
- **float32 のまま使う**: すべての線の `bbox` がわずかに変わります。10進数への復元のコストは PDF-A で約 100ms で、見合うと判断しました。

## 影響

- `scripts/poc_pypdfium2/pdfium_page.py`・`fixtures.py`・`concurrency.py` と `scripts/poc_compare.py` を追加しました。`src/pdf_unit/` の本体は変更していません。
- ADR 0036 の誤りを上記のとおり訂正しました(ADR 0036 にも追記しています)。ADR 0035/0036 で追加した `scripts/poc_bench.py` と `scripts/poc_pypdfium2/poc_lines.py`・`poc_texts.py`・`poc_render.py` は、PoC の記録として残しますが、計測には `scripts/poc_compare.py` を使います。
- 移行を進めるかどうか、進める場合に上記の出力の変化を受け入れるかどうかは、ユーザーの判断を待ちます。
