# ADR 0021: フォント名の文字コードはページ単位で自動判定する

- ステータス: 採用([0014](0014-font-name-encoding.md) の提案のうち、1と5を候補の文字コードを限定して実装)
- 日付: 2026-09-26

## コンテキスト

文字コードが UTF-8 にしか対応していないのではないか、UTF-8・UTF-8(BOM付き)・Shift_JIS・UTF-16・ASCII を自動判定して解釈できるかと質問された。条件として「1ページの中で複数の文字コードが使われることはない」とされた。

各文字コードで本文とフォント名を書いた検証用PDFを作って確認したところ、本文とフォント名で状況が異なった。

- **本文**: PDF の文字列はフォントの Encoding(CMap)で文字コードが宣言されており、pdfminer が `90ms-RKSJ-H`(Shift_JIS)・`UniJIS-UTF16-H`・`UniJIS-UTF8-H` 等の CMap で解釈する。5種類とも正しく「設計図ABC」と抽出できた
- **フォント名**: 文字コードの宣言が無いバイト列で、pdfminer は UTF-8 で読めない場合 `str(bytes)`(`"b'\x82l...'"`)を返す
  - Shift_JIS・UTF-16 は `b'...'` のまま表示されていた
  - UTF-8(BOM付き)は BOM(U+FEFF)が名前の先頭に残っていた

また、Python の cp932 は 0x80 や 0xFD〜0xFF をエラーにせず制御文字・私用領域の文字に割り当てるため、「エラー無くデコードできたら採用」では誤判定する。

## 決定

本文は従来どおり pdfminer に任せ、フォント名だけを `extract.decode_font_names` でページ単位に判定する。

1. pdfminer の `"b'...'"` 文字列は `ast.literal_eval` で元のバイト列に戻す(0014 の1)
2. ASCII だけの名前はそのまま使う
3. BOM(UTF-8 / UTF-16BE / UTF-16LE)がある名前は名前ごとにそれに従う
4. 残りの非ASCIIの名前は、ページ内のすべてをまとめて UTF-8 → BOM無し UTF-16 → cp932 の順に試し、すべてを読める最初の文字コードを使う
   - BOM無し UTF-16 は、全名前が偶数長で 0x00 を含む場合に限り、0x00 が偶数位置に多ければ BE、奇数位置に多ければ LE とする
   - デコード結果に制御文字・私用領域・サロゲートが出る場合は読めなかったとみなす
   - pdfminer が UTF-8 で読めた非ASCIIの名前もこの判定に含める
5. どれでも読めない場合は推測せず PDF の名前表記(`#82l#82r…`)にする(0014 の5)

## 理由

- 「1ページ1文字コード」の前提により、名前単体では区別できないバイト列(例: `C3 BD` は UTF-8 の「ý」とも cp932 の「ﾃｽ」とも読める)を、同じページの他の名前が UTF-8 で読めるかどうかで判定できる
- 候補を質問にあった文字コードに絞ったので、0014 で問題にした gbk・cp949 との取り違えは起きない。UTF-8 は不正なバイト列を厳密に弾くため最初に試し、BOM無し UTF-16 は 0x00 という強い手掛かりがある場合だけにした
- 0014 の埋め込みフォントの `name` テーブルや `CIDSystemInfo` の利用は、依存(`fontTools`)が増えるわりに今回の条件では不要なため見送った

## 影響

- 検証用PDF(Shift_JIS・UTF-16 BOM付き・UTF-8・UTF-8 BOM付き・ASCII)ですべて「ＭＳゴシック」「MS-Gothic」と表示されるようになった
- 1ページ内に異なる文字コードのフォント名が混在すると、誤った文字や `#82` 形式の表記になりうる(前提外)
- GBK・Big5・EUC-JP 等のフォント名は判定対象外。cp932 で読めてしまう場合は誤った文字で表示される
- クリック巡回の「フォント」の一致判定は表示名で行う。同じページ内では同じバイト列が同じ表示名になるので、判定結果は変わらない
