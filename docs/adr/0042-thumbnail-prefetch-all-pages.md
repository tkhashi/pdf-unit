# ADR 0042: サムネイルは開いた直後から全ページを背景で先読みし、表示範囲は優先度を上げる

- ステータス: 採用
- 日付: 2026-09-30

## コンテキスト

[0041](0041-thumbnail-client-side-rendering.md) でサムネイルのラスタライズをブラウザ側(pdf.js)へ移した後も、要求自体は `IntersectionObserver` で検知した表示範囲のページに限っていた。この場合、スクロールしてから該当ページの描画が始まるまでのわずかな遅延が毎回発生する。

100ページ程度のPDFを開いた時点で全ページを一括で描画すると、そのぶん pdf.js のパース・描画処理が積み上がりメモリを圧迫する懸念がある。一方で、1ページずつ順番に描画するだけなら、同時に処理中のページは常に1枚で済む。

## 決定

- 文書を開いたら(`IntersectionObserver` の検知を待たず)全ページを背景優先度でラスタライズ要求キューに積む
- Worker(`thumbnail-worker.ts`)側にジョブキューを持たせ、1件ずつ直列に処理する(同時に処理中なのは常に1ページ)。優先度(数値が小さいほど先)でソートし、可視範囲(優先度0)を背景先読み(優先度1)より先に処理する
- `IntersectionObserver` で表示範囲に入ったページが、まだ背景キューで未処理なら `reprioritize` メッセージで優先度を上げる(描画済みなら無視される)。新規ページ(既に要求済みでないページ)は最初から優先度0で要求する

## 理由

- Worker内の処理を直列(常に1枚ずつ)にすることで、同時に確保するデコード用バッファは1ページ分に収まる。これが実質的な「上限」になり、ページ数が多くてもメモリが際限なく増えることはない
- 可視範囲を優先度で先に処理させることで、スクロール中の体感速度は [0041](0041-thumbnail-client-side-rendering.md) までと変わらない。一方で、スクロールが止まっている間に残りのページも徐々に埋まっていく

## 影響

- `web/src/workers/thumbnail-worker.ts`: ジョブキュー・優先度ソート・`reprioritize` 処理を追加
- `web/src/services/thumbnail-render.ts`: `renderThumb` に `priority` 引数を追加、`reprioritizeThumb` を追加
- `web/src/controllers/thumbnails.ts`: `reset` で全ページを背景優先度(`THUMB_PRIORITY_BACKGROUND`)で登録し、`pump`(可視検知)は優先度を上げる(`THUMB_PRIORITY_VISIBLE`)か、未要求なら新規に優先度0で要求する
- `web/e2e/app.spec.ts` に、開いた直後から全ページが最終的にすべて表示されることを確認するテストを追加した
