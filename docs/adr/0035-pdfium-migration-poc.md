# ADR 0035: pdfplumber から pypdfium2 への移行可能性を、効果測定 PoC で先に確かめる

- ステータス: 採用
- 日付: 2026-09-26

## コンテキスト

API 内部の PDF 処理(線抽出・テキスト抽出・ページ画像化)は、いずれも `pdfplumber` を使っています(`extract_page_lines`・`extract_page_texts` は `src/pdf_unit/extract.py`、`_render_page` は `src/pdf_unit/server.py:193`、線幅補正の正解画像取得は `src/pdf_unit/calibration.py:336`)。一方、サムネイル生成・埋め込み画像抽出・cid 文字補完では、すでに `pypdfium2` を直接使っています。`pdfplumber` は内部で `pdfminer.six` を介して PDF を解析しており、`pypdfium2`(PDFium バインディング)に統一できればパフォーマンス改善が見込めるのではないか、という着想が移行検討の出発点です。

ただし、この移行にはいくつかの制約が絡みます。

- ADR 0023 のとおり、このアプリは抽出結果が元の PDF とどれだけ一致しているかを確かめる用途で、**UX よりも精度が優先**です。推測で最適化に着手せず、計測してから判断する方針を踏襲する必要があります。
- ADR 0011 のとおり PDFium はスレッドセーフでなく、PDFium を使う処理はすべて `_pdfium_lock` 配下で直列化しています。現状、線抽出は `pdfplumber` 単体で完結しておりロック外で並行実行できています。ここを `pypdfium2` に置き換えると、この並行性を失う可能性があります。
- ADR 0010 のとおり、座標は pdfplumber の表示座標系(左上原点、pt、回転反映後)に統一しており、PDFium 由来の座標は `FPDF_PageToDevice` で変換しています。`pypdfium2` 単体で同じ座標系の抽出ができるかは未確認です。

いきなり本実装に着手すると、これらの制約に抵触した場合の手戻りが大きくなります。そこで、本実装の前に、`pypdfium2` 単体でどこまで代替実装ができ、どの程度パフォーマンスが改善するかを、既存コードに影響を与えない形の PoC で確かめることにしました。

また、事前調査で次の点が分かりました。`pdfplumber`(0.11 系)は `page.to_image()` の内部で、`pdfplumber.display.get_page_image()` が `pypdfium2.PdfDocument(...)` を新たに開いて `page.render()` を呼んでおり、すでに PDFium で描画しています。つまり `_render_page`(`server.py:187`)は、`pdfplumber.open()` で開いたページに対し `to_image()` を呼ぶたびに、同じ PDF を PDFium 側でもう一度開き直しています。線・テキスト抽出は `pdfminer.six`(pdfplumber が内部で使う PDF パーサ)経由で PDFium を一切使っておらず、事情が異なります。この違いにより、画像化の PoC で確かめるべきは「PDFium での描画そのものの速さ」ではなく「PDF を開き直す二重コストを避けられるか」であり、線・テキストの PoC で確かめるべきは「`pdfminer.six` の解析を `pypdfium2` の解析で置き換えられるか」であると整理できます。

## 決定

以下の方針で効果測定 PoC を行います。

1. **対象は線抽出・テキスト抽出・ページ画像化の3種すべて**とします。実装コストは処理によって異なりますが(画像化は `pypdfium2` の `render()` で低コスト、線・テキストは高レベル API が無く自前実装が必要で高コスト)、判断材料を揃えるため3種とも試作します。画像化の PoC は「PDFium 描画自体の高速化」ではなく、「`pdfplumber.open()` と `to_image()` 内部の `pypdfium2.PdfDocument()` によるPDFの二重オープンを、`pypdfium2` で一度だけ開く実装に置き換えることで避けられるか」を確かめる位置づけとします。
2. **既存コード(`server.py`・`extract.py`・`calibration.py`)は一切変更しません。** 新規ディレクトリ `scripts/poc_pypdfium2/` に、既存関数と同じ入出力契約を持つ代替実装(`poc_lines.py`・`poc_texts.py`・`poc_render.py`)を並置します。本体コードから PoC モジュールへの参照は作りません(一方向)。
3. **計測は既存の `scripts/profile_pages.py` の切り出しロジックを再利用した新規スクリプト `scripts/poc_bench.py` で行います。** 同一 PDF・同一ページに対して既存実装と PoC 実装を実行し、処理時間・ピークメモリ(`ru_maxrss`)・出力差異を比較します。出力差異は、線・テキストは正規化した値の差分点をリストアップし、画像化は画素差分をレポートします。バイト単位の完全一致は求めず(抽出ロジック自体が異なるため)、座標系や精度を実質的に損なっていないかを確認します。
4. **成功判定は数値閾値を事前に固定せず、定性判断とします。** 処理時間・メモリ・出力差異の実測結果を見たうえで、複数種の PDF で改善が一貫しているか、出力の精度が許容範囲か、`_pdfium_lock` による直列化が全体のスループットを悪化させないかを判断材料にします。3種それぞれで個別に「技術調査フェーズに進むか」を判断してよいこととします。
5. PoC の結果は別途 ADR(0033 を予定)として記録し、技術調査フェーズに進むかどうかの判断とその根拠を残します。

## 理由

- ADR 0023 の「計測してから最適化する」「出力を変えない」という方針を、移行検討にもそのまま適用するためです。移行は「速くなるはずだ」という推測に基づいており、まず実測が必要です。
- 既存 API・レスポンスに影響を与えないことをユーザーから明示的に求められているため、本体コードには一切手を入れず、独立したスクリプトとして PoC を構成します。
- 3種の処理は移行の難易度・リスクが異なる(特に線抽出はロック外並行実行の利点を失うリスクがある、テキスト抽出は cid 補完との連携があり精度リスクが大きい)ため、一括で採否を決めず、処理ごとに判断できるようにしました。
- 数値閾値を事前固定すると、実測前に恣意的な基準を置くことになり、PDF の種類によって改善幅が大きく異なりうる(大判図面か軽量図面か等)実態に合わないため、定性判断とします。

### 採らなかった案

- **本体コードにフィーチャーフラグを入れて A/B 切り替えする案**: 「既存実装に影響がないように」という要求に反するため見送りました。既存コードへの分岐追加自体が影響と見なせます。
- **速度改善◯%以上、といった数値閾値を事前に決める案**: PDF の種類によって改善幅が変わりうること、線・テキスト・画像化で性質が異なることから、実測結果を見てから判断する方が実態に合うと考え見送りました。

## 影響

- `scripts/poc_pypdfium2/` と `scripts/poc_bench.py` が新規に追加されます。`src/pdf_unit/` 配下の本体コードには変更がありません。
- 既存 API のレスポンス・挙動には一切影響しません。
- PoC の実測結果と、技術調査フェーズに進むかどうかの判断は、ADR 0036(予定)に記録します。
