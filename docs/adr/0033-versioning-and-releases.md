# ADR 0033: 版は Git のタグを正とし、リリース PR のラベルで上げる桁を決める

- ステータス: 採用
- 日付: 2026-09-26

## コンテキスト

アプリに版番号を付け、GitHub のタグで管理し、画面にも小さく表示したいという要件がありました。版のルールはリポジトリの管理者が次のように定めました。

- 現在の本番(`main`)を v0.1.0 とする
- `main` へのマージのたびに2桁目を上げる
- 機能の追加・変更がなく、バグ修正や UI のレイアウト調整のような軽微な変更だけのときは3桁目を上げる
- 1桁目は管理者の判断で、よほど大きな変更があるときだけ上げる

あわせて、GitHub の自動生成リリースノートを使いたいという要望がありました。

これまでは、版番号は `pyproject.toml` の `0.1.0` だけでした(`web/package.json` は `0.0.0`)。タグ・リリース・リリースノートの設定はなく、画面にも版は出ていませんでした。`main` への反映は `development` → `main` の PR(merge commit)で行い、そのマージで GitHub Actions がデプロイします(ADR 0021・0022)。

## 決定

- **版の正は Git のタグ `vX.Y.Z`** とします。`pyproject.toml`・`web/package.json` の `version` は更新しません。
- **上げる桁は、`main` にマージされたリリース PR のラベルで決めます。**
  - ラベルなし: 2桁目(既定)
  - `semver:patch`: 3桁目。エージェントが内容を確認して付ける
  - `semver:major`: 1桁目。管理者の指示があるときだけ付ける
  - リリース PR には `release` ラベルも付け、リリースノートの一覧から除きます。
- **デプロイのワークフロー**(`.github/workflows/deploy.yml`)で次のことを行います。
  1. タグを取得する(`fetch-depth: 0`)
  2. `scripts/next_version.sh` で版を決める。マージコミットに紐づく PR のラベルは、GitHub API(`commits/{sha}/pulls`)で読みます。コミットにすでにタグがあれば(再デプロイなど)、その版を使い、リリースは作りません。
  3. 版を環境変数 `APP_VERSION` で UI のビルドに渡す
  4. デプロイと smoke test が成功した後に、`gh release create --generate-notes` でタグとリリースを作る。このため権限に `contents: write` を加えます。
- **リリースノート**は GitHub の自動生成を使い、`.github/release.yml` で PR のラベルごとに分類します(`enhancement`・`bug`・`documentation`・その他)。そのため、`development` 向けの PR には種別に応じたラベルを付けます(`.claude/skills/pr/SKILL.md`)。
- **画面の表示**: Vite の `define` で版を `__APP_VERSION__` として埋め込み、ツールバーのアプリ名の横に小さく表示します。`APP_VERSION` がない手元のビルドでは `git describe --tags --always --dirty` の値を使い、取れなければ `dev` と表示します。
- 最初の版 v0.1.0 は、現在の `main`(React 版 UI・性能計測・出力を変えない高速化を含むリリース)に手でタグを付けてリリースを作ります。

## 理由

- **版上げ用のコミットが要らない**: ファイルに版を書く方式では、リリースのたびに版を上げる PR を `development` に入れる必要があります。ブランチの命名規則(`feat-`/`fix-`/`docs-`)にも当てはまりません。タグを正にすれば、リリース PR にラベルを付けるだけで済みます。
- **判断をリリースの時点に置ける**: 上げる桁は「今回のリリースに機能の追加・変更が含まれるか」で決まるので、リリース PR を作るときが判断に適しています。ラベルなら GitHub の画面でも付け外しでき、管理者が1桁目を上げたいときも同じ手順で済みます。
- **失敗したデプロイに版を付けない**: タグはデプロイと smoke test の成功後に作るので、失敗したときはタグが残らず、再実行すれば同じ版になります。
- **画面の版と本番のコードが一致する**: UI とサーバーは同じワークフローで同時にデプロイされ、画面の版はそのときのビルドに埋め込まれます。
- **リリースノートを手で書かない**: 自動生成なら PR のタイトルから一覧が作られます。ラベルで分類し、リリース PR 自体は除きます。

### 採らなかった案

- **ファイル(`pyproject.toml` など)の版を正にする**: 上記のとおり、版を上げる PR とブランチが毎回必要になるため見送りました。
- **コミットメッセージ(Conventional Commits の `feat:`・`fix:`)から自動で桁を決める**: ルールは「機能の追加・変更の有無」と「管理者の判断」で決まり、`fix:` でも機能の変更を含む場合など、機械的な判定では誤りうるため見送りました。
- **タグをマージ直後(デプロイ前)に作る**: デプロイに失敗した版にもタグが残るため見送りました。

## 影響

- リリース PR にラベルを付け忘れると、2桁目が上がります。
- `development` 向けの PR にラベルがないと、リリースノートでは「その他」に分類されます。
- デプロイのワークフローに `contents: write` と `pull-requests: read` の権限が加わります。AWS の OIDC の条件(`sub`)には影響しません。
- 手元のビルドの版表示は `git describe` の値になります。タグは `main` のマージコミットに付き、`development` からは辿れないため、開発中のビルドでは通常コミットのハッシュが表示されます。本番の版と区別できるので、このままにしています。
