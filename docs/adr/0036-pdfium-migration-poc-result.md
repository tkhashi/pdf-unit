# ADR 0036: pdfplumber → pypdfium2 移行 PoC の結果、3種とも技術調査フェーズに進む

- ステータス: 採用
- 日付: 2026-09-26

## コンテキスト

ADR 0035 で計画した効果測定 PoC(`scripts/poc_bench.py`・`scripts/poc_pypdfium2/`)を、実際の図面 PDF 3種(A0 判・cid 文字を含む大判図面1ページ、軽量な図面5ページ、埋め込み画像を含むページ1ページ)で実行しました。以下は `scripts/poc_bench.py` の実測結果(手元・Apple Silicon)です。

### 線抽出(`extract_page_lines` vs `poc_lines.extract_page_lines_pdfium`)

| PDF | 件数(pdfplumber / pypdfium2) | 時間(pdfplumber → pypdfium2) | ピークメモリ(pdfplumber → pypdfium2) |
| --- | --- | --- | --- |
| 大判図面(cid) | 46800 / 46794 | 4402ms → 954ms(比0.22) | 304MB → 108MB |
| 軽量図面(5ページ平均) | ほぼ一致 | 190〜604ms → 37〜192ms(比0.19〜1.01) | 72〜76MB → 43〜44MB |
| 埋め込み画像ページ | 1851 / 1851 | 128ms → 44ms(比0.34) | 62MB → 43MB |

件数はほぼ一致します(大判図面で6件差。矩形・曲線の分類境界にあるパスの扱いの違いと見られ、原因は未調査)。速度・メモリともに大きく改善しており、特に文字数・図形数の多い大判図面で顕著です(`pdfminer.six` によるページ解析コストが支配的だったことを示唆)。軽量図面5ページ中2ページで比が1.0前後(横ばい)でしたが、これは絶対時間が小さく(200ms未満)子プロセス起動のばらつきの影響が相対的に大きいためと考えられます。

### テキスト抽出(`extract_page_texts` vs `poc_texts.extract_page_texts_pdfium`)

| PDF | 件数(pdfplumber / pypdfium2) | 時間(pdfplumber → pypdfium2) |
| --- | --- | --- |
| 大判図面(cid) | 2235 / 3065 | 4160ms → 436ms(比0.10) |
| 軽量図面(5ページ平均) | 957〜1063 / 616〜627 | 101〜670ms → 19〜135ms(比0.08〜0.37) |
| 埋め込み画像ページ | 53 / 49 | 124ms → 20ms(比0.16) |

速度は3種すべてで大幅に改善しました(最大で1/10)。ただし件数は一致しません。ADR 0035 で見込んだとおり、`pypdfium2` の `FPDFText_CountRects`/`FPDFText_GetRect` は連続したテキスト領域を行・段落に近い単位でまとめるのに対し、pdfplumber の `extract_words` は単語単位で分けるため、grouping の粒度が異なります(大判図面では cid 文字の扱いの違いも件数差に影響していると考えられます)。PoC 実装は cid 文字補完・フォント名デコード・文字ごとの回転や伸縮(`CharGlyph`)も行っていません。

### ページ画像化(`page.to_image()` vs `poc_render.render_page_pdfium`)

| PDF | 解像度 | 時間(pdfplumber → pypdfium2) | 画素差分 |
| --- | --- | --- | --- |
| 大判図面(cid) | 100/200/400dpi | 252ms→164ms / 402ms→213ms / 655ms→495ms(比0.53〜0.75) | 0(完全一致) |
| 軽量図面(5ページ平均) | 100/200/400dpi | 比0.22〜1.39(400dpiの一部ページで悪化・横ばい) | 0(完全一致) |
| 埋め込み画像ページ | 100/200/400dpi | 比0.53〜0.59 | 0(完全一致) |

`pdfplumber`(0.11系)の `page.to_image()` は内部で `pypdfium2.PdfDocument(...)` を新たに開いて `page.render()` を呼んでおり(ADR 0035 のコンテキストで確認済み)、同じ描画設定(`no_smoothtext`/`no_smoothpath`/`no_smoothimage`)を揃えれば**画素単位で完全に一致**しました。これは pdfplumber が実際に PDFium で描画していることの裏付けでもあります。速度は多くの条件で改善しましたが、軽量図面の一部(絶対時間が短い条件)では横ばい・悪化も見られ、`pdfplumber.open()` とPDFiumの二重オープンを避けられる効果は、ページの解析コストが大きい(大判・線数の多い)ほど効いています。メモリは大判図面の高解像度(400dpi)でPoC側がやや大きい傾向がありました(1040MB→1500MB)。

## 決定

3種すべて、ADR 0035 の判定観点(速度改善の一貫性、出力の精度、`_pdfium_lock` の直列化影響)に照らして**技術調査フェーズに進む**と判定します。

- **線抽出**: 速度・メモリの改善が大きく、出力(座標・分類・線幅・色)も実PDFで高い一致率を確認できました。技術調査では、矩形・曲線の分類境界にある少数のパスの扱い、`_pdfium_lock` 配下に移すことによる並行性低下の影響を確認します。
- **テキスト抽出**: 速度改善は最も大きいですが、grouping の粒度(単語 vs 行)が異なる点が最大の技術的論点です。技術調査では、`pypdfium2` 側で単語単位の grouping をどこまで再現できるか(文字単位の座標から自前で分割する必要があるか)、cid 文字補完・フォント名デコードとの統合方法を検討します。
- **画像化**: 画素単位で完全一致し、精度面のリスクが最も低いことを確認しました。技術調査では、`calibration.py` の線幅補正が使う正解画像をこの実装に置き換えた場合の補正結果一致、大判・高解像度時のメモリ増加傾向を確認します。

## 理由

- 3種とも複数の実PDF(大判・cid文字・軽量・埋め込み画像)で速度改善が確認でき、出力(画像は画素完全一致、線は件数・座標がほぼ一致)からも座標系(ADR 0010)を壊していないと判断できるため、技術調査に進める価値があると判断しました。
- テキスト抽出は grouping 粒度の違いという明確な技術的課題が残るため、技術調査フェーズでその解決可能性を見極める必要があります(見送りではなく、調査を経て判断する段階と位置づけます)。
- 数値閾値を事前固定していませんが(ADR 0035)、実測された改善幅(多くの条件で2〜10倍)は誤差の範囲を明らかに超えており、定性判断として十分な根拠があります。

### 採らなかった案

- **画像化のみ次フェーズに進める案**: 画像化が精度面で最も確実な結果(画素完全一致)を示した一方、線・テキストも速度改善が大きく、技術調査で解決を試みる価値があると判断し、3種とも進める判断にしました。

## 影響

- 技術調査フェーズ(ADR 0035 に列挙した項目: 座標系の整合、`_pdfium_lock` 下の並行性、`calibration.py` との整合、依存関係、Lambda 環境への影響、エラーハンドリング、段階移行の可否)を別途スコープとして続行します。
- 本 PoC のスクリプト(`scripts/poc_bench.py`・`scripts/poc_pypdfium2/`)と ADR 0035・0036 は、技術調査フェーズの起点として残します。`src/pdf_unit/` 本体は変更していません。
