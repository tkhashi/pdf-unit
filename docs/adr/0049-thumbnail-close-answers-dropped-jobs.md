# ADR 0049: サムネイルの文書を閉じたら、捨てた未処理の要求にも失敗として応答する

- ステータス: 採用
- 日付: 2026-10-01

## コンテキスト

[0048](0048-thumbnail-worker-page-cleanup.md) と同じ合成PDF(73MB・30ページ)で、サムネイルの先読み中に同じPDFを開き直す操作を計測した。3回開き直して最後の文書の先読みが終わった後、GC してから本体側の JS ヒープを測ると 333MB だった。1回だけ開いた場合は 106MB なので、開き直すたびに約76MB(ほぼPDF1つ分)ずつ増えていた。

原因は、`thumbnail-worker.ts` の `handleClose` にあった。閉じた文書の未着手の描画要求(先読み分)を、キューから黙って取り除いていた。本体側(`thumbnail-render.ts`)は要求ごとに Promise を作って `pending` に登録し、Worker の応答で解決する。応答が来ないと、登録は消えず Promise も解決されない。この Promise の続きの処理(`controllers/thumbnails.ts` の `loadOne`)は閉じた文書の `DocumentSession` を参照しているため、pdf-lib で読み込んだPDF全体が GC されずに残っていた。

大きいPDFほど先読みに時間がかかり、先読みの途中で別の文書を開く機会が増える。そのため、長時間開いたまま文書を切り替えていくと、メモリが際限なく増えていた。

## 決定

- `handleClose` で閉じた文書の未処理の要求を捨てるとき、それぞれに `render-error`(`document closed`)を返す
- 「描画の要求には、成功・失敗のどちらかで必ず1回応答する」ことを Worker の約束事とする。閉じた後に届いた要求は、従来どおり `document not open` の失敗で応答する。描画中に閉じた要求は、pdf.js の描画の失敗として応答する

## 理由

- 本体側の `loadOne` は、失敗の応答を受け取ると、文書が切り替わっていることを確かめて何もせずに終わる。そのため画面の表示は変わらず、Promise と閉じた文書への参照だけが解放される
- 本体側で `pending` を文書ごとに取り消す方法もある。しかし、要求を捨てた Worker 側で応答するほうが、応答の漏れる経路が1か所に限られて単純になる

## 影響

- 同じ操作(先読み中に3回開き直す)の後の本体の JS ヒープは 333MB から 106MB になり、1回だけ開いた場合と同じになった。サムネイルの出力(PNG)は変わらない
