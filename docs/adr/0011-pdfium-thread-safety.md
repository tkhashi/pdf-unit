# ADR 0011: PDFium を使う処理はプロセス全体のロックで直列化する

- ステータス: 採用
- 日付: 2026-09-24
- 追記(2026-09-26): [0038](0038-migrate-to-pypdfium2.md) で線・文字の抽出も PDFium に移行したため、「pdfplumber だけで完結する線の抽出はロックの外に置く」はなくなりました。`/api/page/lines` は、文書を開いてから閉じるまでをロックの中で処理します。

## コンテキスト

ページを切り替えるとサーバーが落ちると報告された。108ページのPDFで、ページ切替時と同じ3リクエスト(線データ・原本画像2解像度)を同時に送ると、サーバーが `exit -11`(SIGSEGV)でプロセスごと落ちることを再現した。

- PDFium(pypdfium2)はスレッドセーフではない
- FastAPI の同期エンドポイントはスレッドプールで並行実行される
- 線データ(線幅補正・cid補完・画像抽出)と原本画像(`page.to_image`)が同時に PDFium を呼んでいた

cid 補完([0009](0009-cid-character-restoration.md))で PDFium の処理時間が増え、衝突しやすくなっていた。

## 決定

- `server.py` に `threading.RLock`(`_pdfium_lock`)を1つ置き、PDFium を使う処理だけを囲む
  - 対象: `page.to_image`、線幅補正、cid 補完、埋め込み画像抽出、サムネイル描画
  - `_lines` の中から `_images` を呼ぶため、再入可能な RLock にする
- pdfplumber だけで完結する線の抽出はロックの外に置き、並行性を残す
- フロント側は、ページを連続で切り替えたとき古いページの応答を捨てる(要求の通し番号で判定)

## 理由

- PDFium 自体を並行化する手段は無いので、呼び出し側で直列化するのが確実
- ロックの範囲を PDFium の呼び出しに絞れば、純 Python の処理は並行のまま動く

## 影響

- 修正後、6ページの順次切替と、16ページ分48リクエストの同時送信で全件成功し、サーバーは落ちなかった
- 重いページの線データ計算中は、原本画像やサムネイルの PDFium 処理が待たされる。サムネイルはフロント側で本体の読み込み完了まで要求を控える([0013](0013-page-thumbnails.md))
- PDFium を使う処理を新たに追加する場合は必ず `_pdfium_lock` の中で行う
